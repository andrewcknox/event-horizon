# Event Horizon LLM README

This file is for future LLM/code-agent contexts. It is intentionally practical and biased toward avoiding wrong-file edits.

## Provenance

This codebase is a cleaned fork of a personal journaling app. Removed in the
fork: the original author's work-hours reporting on category-W events, the
albums list, a survey-export integration, and the author's personal survey
choices, names and keywords. Kept and moved into
`windows/`: the hotkey capture windows (quick journal, lessons, learn-about,
CBT thought record, eye rest), work mode, the capture outbox and the floating
task HUD, all of which used to live in the repo root. `macos/` holds
dialog-based equivalents of the capture scripts for macOS (no HUD there).

The fork is regenerated by a script rather than by hand, so this file describes
the app as it actually ships. Sections that mentioned the removed apparatus in
passing have been rewritten; if you find one that was missed, that is a bug in
the export and not a feature you cannot see.

The installed PWA declares `launch_handler.client_mode` as `focus-existing`,
so installed-app launches focus the existing Event Horizon window instead of
creating another one.

## What The App Is

Event Horizon is a local-first daily journal, task, survey, planning, and native calendar app. It runs a small local Node server and opens the UI in an app-style browser window.

Major surfaces:

- Document/journal capture for a selected day, with Verbatim-style rich formatting.
- Morning and night survey sections.
- Running mistakes log with its own view and output-panel capture tab.
- "Things to learn about" backlog with its own left side-nav view, fed by Ctrl+Alt+L.
- Shopping list with its own left side-nav view, same standing-list shape as the learn backlog.
- Planning and actual tracking.
- Task lists: `rightNow`, `inbox`, `today`, `upcoming`, `completed`.
- Native calendar with plan/actual/both views.
- Settings view for local Google Calendar OAuth setup.
- Floating Windows HUD for the current task with completion/celebration animations.

Run `timezone-transitions` after touching anything in the "Time zones" section —

`coverageSpans()` or `HOUR_COVERAGE_THRESHOLD`. These two counters are only
useful while they are exactly right -- a wrong one either nags about hours that

by looking at the chip.

`deadlinePlanEvents()`, `upcomingDeadlineItems()`, `recurringEventTouchesDate()`
or the `deadlineId` field. The nag's contract — shows until a work block is
booked, then stops — fails silently in both directions: a deadline that nags
forever trains the list to be ignored, and one cleared by the wrong evidence (a
past block, an actual block, someone else's block) hides real unplanned work.

Run `task-peg` after touching `peggedTaskFollowTarget()`, `findTaskRefById()`,
`peggedTaskDueDateChange()`, `followPeggedTaskDueDate()` or the task storage
helpers they stand on (`taskStorageDate()`, `tasksForDate()`, `taskRef()`). A peg
writes to a file the user is not looking at, and both failures are silent: too
eager and an archived or `actual` block reschedules a task backwards, too shy and
the calendar quietly lies about when the work is due.

Run `task-parse` after touching `parseTaskInput()` or any of its `parseTask*At`
helpers. Every parser mistake is destructive in the same quiet way — a word it
wrongly claims disappears out of the task title — so the suite covers what must
*not* parse as much as what must.

Run `trends-process` after touching the Trends "process" cards, the calendar
`createdAt` fields, or the goal event kinds.

Run `data-backup` after touching `writeDataFile()`, `writeJsonFile()`,
`checkDataWriteGuard()`, `archiveDataFile()`, `snapshotDataFileDaily()` or
`DATA_FILE_POLICY`. It extracts the real block out of `server.cjs` by name, so a
rename breaks the harness rather than silently skipping the checks. What it pins
is the pair that is hard to hold at once: the guard must refuse 856 events being
replaced by nothing, and still allow an ordinary bulk delete, a short list being
emptied, and every write that only grows. It also pins that the OAuth files stay
out of the backups.

Run `goal-task-expiry` after touching `ensureDailyGoalTasks()`,
`expireDailyGoalTasks()`, `taskExpiryDate()`, or the goal `surface`/`expires`
fields in `goals.json`. It extracts the real functions from `app.js`, so a
renamed function breaks the harness rather than silently skipping the checks.

Run `entry-sync` after touching `syncTasksFromDisk()`, the task merge, the 409
recovery in `performEntrySave()`, the fingerprint helpers, or the `/api/tasks`
payload. **`server.cjs` changes need the server restarted**
to take effect; `app.js` and `styles.css` are served from disk, so a browser
reload is enough.

For frontend behavior, use the local browser at `http://localhost:8787` or `http://127.0.0.1:8787` and check the browser console for errors.

## Data Files

- `entries/YYYY-MM-DD.json`: daily document, survey, planning, tasks, mistakes.
- `entries/.history/YYYY-MM-DD/`: automatic pre-save entry versions (latest 30 per date). A copy is only written when the incoming entry differs from the one on disk apart from `_revision`/`_savedAt` — the 350 ms save debounce used to fill this with near-identical copies, which is how it reached 5,533 files / 49 MB and pushed genuinely distinct older versions out of the window. Dates written before that change keep their old backlog until the next save to that date prunes them.
- `entries/.conflicts/YYYY-MM-DD/`: rejected stale-window saves (latest 50 per date).
- `exports/YYYY-MM-DD.md`: markdown export.
- `calendar-events.json`: native calendar events.
- `timezone-history.json`: one row per zone change, each pinned to an instant. Written by `POST /api/timezone-history`; `SEED_ZONE_TRANSITIONS` in `server.cjs` (empty by default) is written on the first read of a machine with no file, for anyone importing history lived in more than one zone. See "Time zones" below — this file is what every hours total in the app is counted against, so a wrong row here is a wrong number everywhere.
- `google-calendar-config.json`: local Google OAuth client settings, created by the Settings view setup panel. Treat as sensitive.
- `google-calendar-auth.json`: local Google OAuth tokens, created after Google sign-in. Treat as sensitive.
- `google-calendar-push.json`: ledger of which local plan block was pushed up as which Google event. Not sensitive, but deleting it orphans every pushed event on Google.
- `app-settings.json`: active view/date, UI settings, calendar mode/filter.
- `spotify-config.json`: local Spotify app client ID and secret, created by the Settings view panel. Treat as sensitive.
- `spotify-auth.json`: local Spotify OAuth tokens plus the poller's bookkeeping (`lastSyncAt`, `lastError`, `needsReconnect`, `nowPlaying`). Treat as sensitive. Deliberately has no `DATA_FILE_POLICY` entry so no copy of a token lands in backups.
- `spotify-listens.json`: append-only log of every Spotify play, one row per play (`playedAt`, `track`, `artists`, `album`, `durationMs`, `uri`, `contextUri`, ...). Written only by the server's poller. See "Spotify listening log".
- `custom-choices.json`: custom survey/category choices.
- `goals.json`: goal definitions, context schedule, rule-of-the-day schedule.
- `goal-log.json`: append-only goal check-in events. Never merged into entries.
- `monthly-reviews.json`: the −5..+5 monthly retrospectives, object-shaped
  (`months` keyed by `YYYY-MM`), written by `POST /api/monthly-review` through a
  serialised month-scoped chain. Months imported from the old workbook carry
  `imported: true` and keep their own row order. No part in the entry revision
  model — see "Monthly review" below.
- `eyerest-log.json`: append-only eye-rest session history, written by `POST /api/eyerest`. Never merged into entries; kept separate from `calendar-events.json` so it can be analyzed without cluttering the calendar UI.
- `eyerest-settings.json`: last-used eye-rest countdown length, read/written directly by `eyerest-capture.ps1` (same pattern as `hud-settings.json`/`task-hud.ps1` - not served through the HTTP API).
- `eyerest-draft.txt` / `eyerest-draft-discarded.txt`: manual-recovery copies of the blind-journaling box (autosave during a session / text parked by a Discard click). Written directly by `eyerest-capture.ps1`; nothing reads them back.
- `learn-list.json`: standing "things to learn about" backlog, written by `POST /api/learn-list` and its `/update` + `/delete` siblings. Never merged into entries - it is a cross-day list, not a dated log.
- `albums.json`: standing album list, written by `POST /api/albums` and its `/update` + `/delete` siblings. Same cross-day rules as `learn-list.json`. Deliberately separate from the night survey's `album-reviews` answers, which stay in entries and are never migrated -- see "Albums" below.
- `shopping-list.json`: standing shopping list, written by `POST /api/shopping-list` and its `/update` + `/delete` siblings. Same cross-day rules as `learn-list.json`.
- `eyerest-state.json`: current eye-rest stage (`idle`/`running`/`review`), the last `outcome` (`logged`/`discarded`) and `changedAt`. Written by `eyerest-capture.ps1` on every stage change and at launch; read by `work-mode.ps1` to pause its pomodoro. Not served through the HTTP API on purpose - see "Work Mode".
- `work-mode-settings.json`: band thickness, pomodoro length, pill position, and the distraction pattern/process lists. Read once at launch by `work-mode.ps1`, written on every tray change. Absent until something is changed; the built-in defaults are in the script.
- `work-session-state.json`: the work session currently open, heartbeated every 10s by `work-mode.ps1`. Present only while the band is on; a file left behind by a killed process is what `Restore-WorkSession` books on the next launch. See "Work sessions on the calendar".
- `work-mode-log.json`: last 500 work-session decisions (start, posted, skipped-short, recovered, gap split). Diagnostic only - nothing reads it back. First place to look when a work block is missing from the calendar.
- `hud-settings.json`: HUD window size and position.
- `hud-log.json`: append-only HUD lifecycle log, written by `POST /api/hud-log`. See "HUD usage logging" below.
- `app-log.json`: append-only app session log (page load, tab focus, view switches), written by `POST /api/app-log`. Same shape as `hud-log.json`.
- `task-log.json`: append-only record of task reschedules, written server-side by `saveEntry` when it sees a task's section or due date change. Nothing in the frontend writes it.
- `browser-profile-clean/`: browser profile used by the app-style window.
- `backups/history/<file>/<utc-stamp>-<hash>.json`: the contents of each data file as they were immediately before every write, newest last, capped per file by `DATA_FILE_POLICY` in `server.cjs`. Content-addressed, so a rewrite identical to what is already stored does not consume a slot — the client POSTs the whole calendar on every edit whether or not the edit touched it, and without the hash an idle afternoon would push the last genuinely different version out of the window.
- `backups/daily/YYYY-MM-DD/<file>`: one copy per data file per **local** calendar day, holding that day's starting state. Kept 60 days. This is what outlives history rotation: the calendar is written dozens of times a day, so its rotating copies span hours, not months.
- `backups/rejected/<file>/`: payloads the write guard refused. Never written to the live file. If a refusal was wrong, this is where the intended version is recovered from — the guard must never itself be the reason an edit is lost.
- `backups/pre-restore/<file>/`: whatever `backup-restore.cjs restore` overwrote, so restoring the wrong version is itself undoable.

Be careful with user data files. Do not overwrite them with generated examples. If testing data edits is necessary, make a backup first and restore it.

### Data file writes go through one function

`writeDataFile()` in `server.cjs` is the only correct way to write a data file, and `writeJsonFile()` is a thin wrapper over it. It guards, archives the previous contents, snapshots the day, then writes atomically. Do not reintroduce a bare `fs.writeFile` on any of these paths: a plain truncate-then-write loses the file outright if the process dies mid-write, which is what every one of these call sites used to do.

The guard is the layer that matters, and it exists because of a specific near-miss on 2026-08-17. `server.cjs` was down; the app came up from its cached service-worker shell with an empty calendar (`loadCalendarEventsFromDisk()` fails soft, and `calendar-events.json` is deliberately absent from the localStorage snapshot); the next calendar edit would have POSTed `[]` over 856 events, with no second copy anywhere on disk. A backup alone would not have saved it — nobody would have noticed in time. The write itself has to be refused.

Row counts are the signal, and `DATA_FILE_POLICY` sets the rule per file:

- `append-only` (the logs): any shrink at all is a bug.
- `shrink` (the calendar, the lists): refuses only a collapse — more than `DATA_GUARD_MAX_LOSS` (half) of the rows in one write.
- `none` (object-shaped files): history, no guard, because there is no row count worth comparing.

Files under `DATA_GUARD_MIN_ROWS` (20) are never guarded; 3 → 1 is an ordinary afternoon on the shopping list. Object-shaped payloads are never guarded whatever their policy, since `dataRowCount()` only counts arrays.

The OAuth files are **deliberately absent** from the policy table. They hold long-lived refresh tokens, and quietly fanning copies of a credential across dozens of files on disk is a worse problem than the one the backups solve. They still get the atomic write. `tests/data-backup.test.js` pins this — if you add them to the table, that suite fails.

`loadCalendarEventsFromDisk()` retries on a 3 s → 30 s backoff until it succeeds, and retries immediately when the tab becomes visible. It used to load once at startup and never again, so a server that was down for the twenty seconds the app happened to boot in left an empty week on screen for the whole session — indistinguishable from a real empty week, and only cleared by the user thinking to reload. This happened twice on 2026-08-17, the second time while another window was restarting the server. The calendar is the one view with nothing behind it in localStorage, so it is the one view that must recover on its own. Do not reduce this back to a single load.

A refusal is not automatically correct: a genuine bulk delete trips the same wire. `POST /api/calendar-events` answers `409` with `code: "data-write-guard"` and the before/after counts, and `postCalendarEvents()` in `app.js` asks the user in those terms before re-sending with `force: true`. Never make the guard unoverridable, and never let that 409 be swallowed silently — the old `.catch(() => {})` on this path is exactly how a refused save could read as a successful one.

The server normalizes tasks and calendar events. Keep frontend/server schemas in sync.

`GET /api/calendar-events` answers `500` when the file exists but cannot be read or parsed, and `200 {events: []}` only on `ENOENT`. The distinction is load-bearing: an empty array is the app's signal for "you have no events", so reporting an unreadable file as an empty one puts the app one edit away from POSTing that emptiness back. `POST /api/calendar-events` answers `409` with `code: "data-write-guard"` when the write guard refuses it, and takes `force: true` in the body to override — see "Data file writes go through one function".

Entry saves use optimistic revisions. The frontend must send `expectedRevision`; the server rejects stale or legacy whole-entry writes instead of overwriting a newer entry. On startup, the disk entry is authoritative over browser local storage. Do not remove these safeguards or restore blind whole-entry writes.

Static assets are served `no-cache, must-revalidate` with an `ETag` built from size + mtime. `no-cache` is not `no-store`: the browser still asks the server on every load, so a stale `app.js` can never run — which is the property that matters, since an old client can clobber newer entry data on save — but an unchanged file comes back 304 with no body. That is ~538 KB per phone load over the network that no longer moves. Do not "simplify" this back to `no-store`, and do not add a `max-age`, which would let a stale bundle run without asking.

`writeJsonAtomic()` retries the rename up to 5 times. On Windows the swap fails outright when a scanner or the indexer holds the destination for a moment; without the retry the save was lost and the temp file orphaned. `sweepOrphanedTempFiles()` clears `*.tmp` older than an hour at startup.

## Frontend State Notes

Main state lives in `app.js`.

Important variables:

- `state.entries`: daily data keyed by date.
- `state.calendarEvents`: local calendar event array.
- `activeView`: document/tasks/calendar/mistakes/learn/shopping/albums/survey/settings/trends.
- `calendarMode`: month/week/day.
- `calendarCursorDate`: date currently being viewed.
- `calendarKindFilter`: `plan`, `actual`, or `both`.
- `calendarDragSelection`, `calendarResizeState`, `calendarEventMoveState`: calendar pointer interactions.

`localStorage` is *not* a mirror of `state`. `localSnapshot()` writes only the last 45 days of entries plus the day on screen, and drops `state.calendarEvents` entirely — those live in `calendar-events.json` and `loadCalendarEventsFromDisk()` replaces them wholesale at boot. Writing the whole state cost a synchronous ~730 KB stringify on every 350 ms debounce tick and was heading for the ~5 MB quota. `writeLocalSnapshot()` never throws: it retries with a narrower window and finally gives up, because a `QuotaExceededError` escaping `saveLocal()` used to abort `saveEverywhere()` *before* its try block and silently take the disk save — the durable one — down with it. Anything added to `state` that is not also on disk needs to be considered here.

Task sync cadence: 1.5 s while visible, 15 s while `document.hidden`, switched by `applyTaskSyncCadence()` from the `visibilitychange` handler in `wireEvents()`. That handler also runs the immediate catch-up poll on the way back, so `applyTaskSyncCadence()` deliberately does not.

Important task sync guard: `syncTasksFromDisk()` polls the server and can re-render the task view. Never let that run while the user is typing in any task UI field, including quick-add and section add inputs, or their typed text will disappear about once per polling interval. Task inputs should have `data-task-editor`, call `deferTaskSync()` on focus/input where appropriate, and `isTaskTextEditing()` must continue to treat any focused `input`, `textarea`, `select`, or contenteditable inside `#tasksView` as an active edit.

Task semantics: `inbox` is unsorted capture and older inbox items carry forward in the UI, except tasks carrying an `expiresOn` (see "Daily goal tasks expire" under Goals); every row that is not for the day being viewed says so via `taskDateNote()`, because an inbox of undated repeats is unreadable; `today` is the selected date's committed list; `rightNow` is the ordered focus stack and the only source for the page's "Current task" and the HUD. When `rightNow` is empty, no current task is shown. The quick field directly below "Current task" always inserts at the front of `rightNow`, independent of the selected task filter. `today` renders in automatic priority tiers (P1 top through P4 bottom) via `sortTodayTaskItems()`; inside one tier the stored array order wins, so dragging a row is the manual ordering. Dragging in `today` and `rightNow` reorders live: `previewTaskDrag()` moves the row on `dragover` (clamped to the dragged task's own tier in `today`), `commitTaskOrderFromRows()` writes the on-screen order back on drop, and a cancelled drag re-renders from storage. `taskDragState` also blocks `syncTasksFromDisk()` so a poll cannot re-render mid-drag. Other sections still use `compareTaskItems()` and the older `moveTask()` drop path. `overdue` is a derived, non-persisted view: an incomplete task with a due date before the real `todayISO()`, or an undated task left in an earlier date's `today` list, is overdue. Never calculate overdue status from the date the user is browsing. The Calendar and Tasks left rail shows this compact queue instead of a calendar agenda.

### Estimates and placing a task on the calendar

A task carries `estimateMinutes` (0 = not estimated). It has exactly one job:
sizing the block the task drops as. `normalizeEstimateMinutes()` exists in both
`app.js` and `server.cjs` and both copies must agree — like `goalId` and
`expiresOn`, a field missing from either `normalizeTask()` is silently dropped on
the next save.

A task also carries `calendarCategory`: the category letter its block is filed
under, decided **before** the placement so a placed block never needs a second
edit to be coloured and counted. It is validated against `CALENDAR_CATEGORIES`
(`normalizeCalendarCategory()`, mirrored in `server.cjs` against
`calendarCategoryCodes`). Three ways it gets set, in priority order:

1. The goal, for materialised daily-goal tasks: `calendarCategory` on the goal in
   `goals.json` (`15 LinkedIn points` → `B`). `ensureDailyGoalTasks()` copies it
   onto the task. Unlike the text and the estimate, it only **fills a blank** —
   a goal that stamped over today's row every render would make the row control
   a lie — which is also what backfills tasks created before the field existed.
2. The row: the one-letter select in `.task-meta` (`taskCategorySelect()`),
   between the estimate and the date.
3. Neither: `taskCalendarCategory()` falls back to `categorize()`, the same
   keyword matcher the hours log uses, so "gym session" resolves to `E` with
   nothing configured. Blank in the select therefore means *auto*, not *none*,
   and the option shows the current guess (`·E`).

`taskCalendarCategory()` is resolved when the task is picked up, not when it is
dropped: the cursor bubble and the draft preview both carry the category colour
(the preview reads `--draft-accent`, set by `renderCalendarDraftPreview()`'s
`color` option), so a wrong guess is visible before the click. The category rides
in `taskPlacement.category` and lands on the event, where
`normalizeCalendarEvent()` derives the block colour from it. Nothing sets
`workCategory`/`workAssignedBy` for a `W` task — those columns are only required
of `actual` sessions by the work-hours export, and placement writes `plan`.

Placement is a click-to-arm mode, not HTML5 drag-and-drop: rows are already
draggable for reordering, and a second drag meaning would collide. Pressing the
`◷` button on a task row or a rail row calls `startTaskPlacement()`, which parks
the task in `taskPlacement`, switches to the Calendar view (and out of month
mode, which has no times), and hangs a bubble off the cursor.
`startCalendarSlotDrag()` checks `taskPlacement` first, so the next click on a
slot goes to `placeTaskOnCalendar()` instead of starting a drag-selection; the
event is written at the snapped time under the pointer, running for the estimate
(defaulting to `TASK_PLACEMENT_DEFAULT_MINUTES`). Escape cancels.

The task is **not** consumed by being placed — planning when to do something is
not doing it, and a task that vanished into the calendar would stop being
tickable.

Placing a task on a day it is not due **is** a reschedule (user request,
2026-08-27): `placeTaskOnCalendar()` routes through `updateTaskMeta()` with the
placed date as `dueDate`, which also moves the row into that day's `today` list,
and the save-status line says so ("due date moved to …"). Same-day placement
changes nothing — an undated task placed on the day it already lives stays
undated. Deadline placements (`startDeadlinePlacement`) carry no `taskId` and
are untouched.

A placed event carries `taskId` back to the task (a third field that must exist
in `normalizeCalendarEvent()` in **both** `app.js` and `server.cjs`). That is
what `scheduledPlanEventForTask()` reads to fill the `◷` button in
(`.is-scheduled`) when a task already has a time — the indicator deliberately
reuses the existing button rather than adding a badge, so a row costs no extra
space. It resolves the **earliest plan block from the viewed date onward**;
a past block is history, and treating it as a schedule would leave every task
permanently lit. An unlinked plan event whose title equals the task text counts
too, so days planned by hand — which is how they were planned before the button
existed — light up the same way.

### Pegging a task to a block: the block is the schedule

`taskId` on a plan block is a two-way arrangement, not just a record of the
placement that made it. Moving the block moves the task: drag "Deck work" from
Sunday to Tuesday and "Draft the pitch deck" is due Tuesday, the row moving into
that day's `today` list the same way `updateTaskMeta()` moves it from anywhere
else. Replanning then happens once, on the calendar, instead of twice in two
places that drift apart.

Not the same peg as `tz`, which pegs an event to a time zone. Same word,
different rope.

Four functions, in `app.js` only (nothing about this is server-side; `taskId`
was already carried by both normalisers):

- `peggedTaskFollowTarget(event)` — the day a pegged task should be due, or
  null. Current plan blocks only. An `actual` block carrying `taskId` is a
  record of work already done and an archived one (`supersededAt`) is a plan
  reality overtook; following either would drag a task backwards into history.
- `findTaskRefById(id)` — the open task with that id, wherever it is filed. The
  section is confirmed through `taskRef()` rather than trusted from the scan,
  which is what keeps the dead `rightNow` lists out: every rightNow lookup goes
  to today (`taskStorageDate()`), so the rightNow arrays sitting in older entry
  files are unreachable storage, and writing a due date into one would be a
  write the app never reads back. Completed and discarded tasks are not
  searched — a task that is done has no due date left to move.
- `peggedTaskDueDateChange(event, found)` — what the move does, decided before
  anything is written. `dueDate || ref.date` is the same reading of "what day is
  this task for" that placement uses, so pegging an undated task to a block
  dates it. Landing on the day it is already due changes nothing: 09:00 to 14:00
  is not a reschedule.
- `followPeggedTaskDueDate(eventId)` — the only one that writes. It takes an id
  because every caller runs after `normalizeCalendarEvents()`, which rebuilds
  every event object.

Three commit paths call it, and they are the three ways a block's day can
change: `finishCalendarEventMove()` (a plain drag), the `finish()` inside
`promptRecurringDragScope()` (a repeating block, once the scope question is
answered — it is handed the id of the detached occurrence or the split
successor, which are new records), and `closeCalendarEditorAfterChange()` (a
date typed into the editor, or a peg set there). `placeTaskOnCalendar()` keeps
doing its own reschedule; the rule is the same one.

The link is only ever the explicit `taskId`. `scheduledPlanEventForTask()` also
counts an unlinked block whose title matches a task, which is right for lighting
the `◷` indicator and wrong here: a block called "gym" must not silently
reschedule a task called "gym" that nobody connected to it. The editor's
**Pegged task** select (`calendarTaskPegField()`, plan blocks only, hidden with
the kind) is how a block drawn by hand gets the link, and `calendarEventFromForm()`
reads the control only when the editor rendered it — a provider event's form has
no such row and must not have its peg wiped. Provider events are not offered the
row at all: nothing here can drag them, and the sync merge in `server.cjs` only
carries `kind`, `category`, `color` and `exceptionDates` across an import, so a
peg set on one would not survive the next sync.

The same select offers a task that does not exist yet: **+ New task from this
block…** reveals a name box (seeded from the title as typed) and creates the
task on Save. `NEW_PEG_TASK_VALUE` (`"__new__"`) is a sentinel, deliberately not
an id — nothing is written until the block is, so a peg started and abandoned
leaves no orphan task. `taskPegIdFromForm()` does the creating and remembers the
new id on the select (`dataset.createdTaskId`), because the form is read more
than once on the way to being saved: the recurring-scope chooser re-reads it
after asking, and a split reads it for each half, and every read after the first
has to find the same task rather than make another. That chooser is also why
`saveCalendarEventFromForm()` passes `createPegTask: false` on the build that
precedes the question — that build is thrown away, and cancelling the chooser
must not leave a task behind for an event that was never saved. A row left on
the sentinel while the kind is switched to actual or deadline writes nothing:
only a plan block can be pegged. `createPeggedTask()` files the task under the
block's own day (`today`, dated — a peg needs a due date to be able to move one)
with the block's length as `estimateMinutes` and its category as
`calendarCategory`, so it can be dropped back on the calendar later without
being re-decided; the quick-add grammar still runs on what was typed.

A pegged block wears `◷` in front of its title and says so in its tooltip.
That is not decoration: dragging one writes to a task in another view, and a
side effect nothing on screen announces is one discovered by accident. The same
reasoning is why the move is reported. It rides the save line rather than being
written just before it — `saveEverywhere({ status })` appends it to
`Saved 7:06 AM`, because a message set before the save resolves is overwritten
milliseconds later by the save's own line.

## Document View Formatting

The Document view is a rich contenteditable (`#journalDoc` inside
`#documentEditor`, with a generated toolbar in `#docToolbar`), not a textarea.
All of it lives in one marked section at the end of `app.js` (`wireDocumentEditor`
and the `doc*`/`applyDoc*` helpers) plus one section at the end of `styles.css`.

### The plain-text mirror is load-bearing

`entry.journalHtml` is what the editor loads and saves. `entry.journal` is a
plain-text mirror rebuilt by `docPlainText()` on every edit, and it stays the
authority for everything downstream: `extractHours()`, search, the Missing tab,
the workbook TSV, and the Copy Document text. Nothing outside the editor section
should know about markup, and nothing outside it may write `entry.journal` —
a write there would be silently replaced by the next mirror rebuild.

`ensureEntry()` promotes a legacy plain-text day into paragraphs once, so days
written before formatting existed open normally.

Block elements become newlines and table cells become tabs in the mirror, which
is what keeps `09:00-10:00 gym` on a single line for the hour parser.

### Undo is ours, not the browser's

Block styles, tables and condense mutate the DOM directly, which invalidates the
browser's own contenteditable undo transactions. So `docUndoStack`/`docRedoStack`
hold HTML snapshots with a child-index path to the selection, Ctrl+Z/Ctrl+Y are
intercepted inside the editor and never reach the browser, and ordinary typing
coalesces into one snapshot per `DOC_SNAPSHOT_IDLE_MS` burst.

`handleGlobalUndo()` must keep skipping events from inside a contenteditable via
`closest()`, not `matches()`: the keydown target there is the element holding the
caret (a `p`, an `li`, a `td`), so a `matches()` check let Ctrl+Z through to the
app-wide undo and rewound the whole day.

### Rendering must not fight the caret

`renderDocumentEditor()` skips writing `innerHTML` when the day is unchanged and
either the markup already matches or the editor has focus. Without that, every
`render()` — and there are many — would drop the cursor mid-sentence.
`syncDocumentText()` refuses to write when `docLoadedDate` is not the entry's
date, which is what stops a pre-date-switch flush from copying one day's document
into another.

### Sanitising, and the deliberate absence of fonts

Everything entering the editor goes through `sanitizeDocHtml()`: an allowlist of
tags, of classes (`DOC_ALLOWED_CLASSES` — these are the same names the CSS styles,
so renaming one strips it off every saved day), and of style properties.
`font-family` is deliberately not on that list. The user asked for
Google-Docs-grade formatting *without* font choice, so the surface keeps one
typeface, pasted fonts are dropped, and `<font>` tags are unwrapped. The size
ladder is in points to match how Word and debate cards are talked about.

Highlights are `<mark>` rather than a bare background colour so night mode can
pin dark ink on the pastels; an inner colour span still wins over it.

### Verbatim behaviour

Styles follow paperless-debate Verbatim: Pocket > Hat > Block > Tag as h1..h4,
plus Cite and Analytic. Underline mode (F9) and highlight mode mark text the
moment you select it and then collapse the selection, which is why they fire on
`mouseup` only — on keyup they would collapse a shift+arrow selection that was
still being extended. Shrink (Ctrl+8) reduces everything in the selection except
underlined runs, measuring the base size *before* wrapping because applying
`fontSize` drops the size already on the run. Clear formatting keeps highlighting
(Verbatim's behaviour); the menu holds a clear-everything variant.

### Other notes

- `docWrapSelection()` gets its own spans by applying legacy `fontSize` and
  swapping the resulting `<font>` tags. Its callback runs with the span already
  in the document so computed styles are readable, and may return a replacement
  element.
- The Journal output tab is a read-only formatted preview (`.doc-preview`). It
  used to be a second plain-text box bound to `entry.journal`; editing there now
  would either lose the markup or be overwritten by the mirror.
- Markdown export converts the HTML (`docMarkdownFromHtml()`), so headings,
  lists, highlights (`==x==`) and tables survive into `exports/YYYY-MM-DD.md`.
- Copy Document puts `text/html` and `text/plain` on the clipboard, so pasting
  into Word or Google Docs keeps the formatting, and falls back to `copyText()`.
- Toolbar state refreshes through `setTimeout`, not `requestAnimationFrame`: rAF
  is paused while the window is hidden, which froze the toolbar and word count.

### Pictures in the document

`IMG` is on `DOC_ALLOWED_TAGS`, but the sanitizer admits an image **only when
its `src` matches `DOC_IMAGE_SRC_PATTERN`** (`/entries/media/…`, the server's
own media store). A remote URL would break offline and leak reads to the wider
internet; a `data:` URI (what a Word paste carries) would balloon every entry
save, history snapshot and backup the day owns. Both are dropped outright — an
`<img>` has no children, so unwrapping would leave nothing anyway. Only
`src`/`alt` survive attribute stripping.

Three ways in — paste, drag-drop, and the 🖼 toolbar button (the phone path;
it opens the camera roll). All of them go through `insertDocImageFiles()`:
downscale on the client (`docImageDataUrl()`, max 1800 px, JPEG 0.85 — a phone
photo is 4–12 MB and `/api/survey-image` caps at 4 MB; small PNGs pass through
untouched so screenshots keep sharp text), POST to `/api/survey-image` with
`questionId: "doc"` — the same endpoint and `entries/media/<date>/` store the
night survey's picture questions already use, so the server needed no new code
— then `insertHTML` an `<img>` at the caret via `docFocusEditor()`. If the
selected day changed while the upload ran, the insert is refused rather than
landing in the wrong day's document.

The markdown export writes `![alt](src)` (the IMG branch in
`docMarkdownInline()` must stay **above** the empty-inner shortcut, which would
otherwise swallow it). The plain-text mirror ignores images, so the hour parser
and search are unaffected.

### The Journal tab is a reader

`renderJournalOutput()` still renders the read-only `.doc-preview`, but the tab
now reads backwards through the archive: scrolling near the bottom appends the
previous non-empty day under a clickable date divider
(`appendNextJournalReaderDay()`, stepping over empty days, 120-day lookback),
and the ‹ › arrows move a **reader date** that is deliberately separate from
`state.currentDate` — changing the app date would reload the editor and the
surveys underneath the reader. Clicking a divider does switch the app to that
day. A date change in the app resets the reader to it.

The rebuild guard matters: `renderOutputs()` runs on every 350 ms save while
typing, so the reader skips the rebuild when its signature (start date,
appended dates, current day's html length) is unchanged, and carries
`scrollTop` across when it is not — without that the tab snaps to the top
mid-read on every keystroke. The scroll listener is attached once in
`wireEvents()` because only the panel's children are replaced, never the panel.

## Mistakes Log

A running log kept through the day, stored as `entry.mistakes` on the per-day
entry: `{ id, time, ts, loggedAt, what, problem, why, alternative, nextTime }`.

`time` is the human-readable clock string shown in the UI. `ts` and `loggedAt`
are the two machine timestamps and they are not the same thing: `loggedAt` is
when the row was typed and is always set; `ts` is when the mistake actually
happened. The capture window (`mistake-capture.ps1`) has a **"This happened
today" checkbox, ticked by default**; unticking it reveals a `YYYY-MM-DD` box and
files the mistake under that date with `ts: null`, because the date is known but
the hour is not. Adding a mistake in-app while viewing a past day does the same.
Never backfill `ts` from `loggedAt` — a wrong hour is worse than no hour, and
time-of-day is the axis these rows exist to support. The text fields
are the columns defined by `MISTAKE_COLUMNS` in `app.js`; that constant drives
the view, the TSV copy, the markdown export, and the Missing tab, so add columns
there rather than in each renderer.

`alternative` ("Alternative explanation" — context outside the user's control,
or reasons it may not be a mistake at all) is a therapist-prescribed counterweight
to the self-blaming `why` column, which is why it sits directly after it with the
action column last. Do not reorder them.

Adding a column means touching three places: `MISTAKE_COLUMNS` and
`normalizeMistake()` in `app.js`, the constructed row in `addMistake()` in
`server.cjs`, and a `TextBox` plus its `FindName`/payload/reset lines in
`mistake-capture.ps1`. `normalizeMistake()` spreads the source object first so
unknown keys survive — without that, a browser window running an older `app.js`
strips any newly added column on its next whole-entry save.

The design point that matters: capture and completion are deliberately split.
`what` is filled the moment the mistake happens; the other three are reflective
and get filled later. A row with only `what` is valid and merely counts as
unfinished — do not add validation that requires all four at capture time, and
do not move capture into the night survey. The user specifically does not want
this gated behind an end-of-day form.

Surfaces:

- `mistakes` view (side nav) — `renderMistakesView()`. Quick-capture field plus
  one card per row with all four columns. Unfinished rows get `is-unfinished`.
  The `All days` toggle (`mistakesReviewOpen`) reads across `state.entries`,
  which already holds every entry from `/api/entries`, so no server call is
  needed; clicking a date jumps to that day.
- `mistakes` output-panel tab — `renderMistakesOutput()`. Reachable from any
  view so a mistake can be logged without leaving what caused it. It logs to the
  currently selected date and says so when that is not today.
- Missing tab chases blank columns on rows already captured. An empty log is not
  reported as missing; a day with no mistakes logged is legitimate.

View containers in `#workArea` are toggled only by the `hidden` class. Any rule
setting `display` on one of them must sit **above** `.hidden` in `styles.css`, or
it wins on equal specificity and that view never hides — it keeps its
`height: 100%` slot and pushes the active view off-screen, which looks exactly
like the active view rendering blank. `.hidden` now carries `!important` as a
backstop, and nothing sets `display` inline, so keep it that way.

`ensureMistakeState()` normalizes rows **in place**. `ensureEntry()` runs on
every `currentEntry()` call, so replacing the row objects would orphan the
textareas bound to them and the open editor would silently stop saving.

### Capture window (Ctrl+Alt+W)

`mistake-capture.ps1` is a background WPF listener with no visible window until
the global hotkey fires, then it shows a four-box capture window. Ctrl+Enter
posts and hides, Esc hides. It is deliberately **not** part of `task-hud.ps1`:
capture must keep working when the HUD is closed.

- `launch-mistake-capture.ps1` starts the local server if needed, then the
  listener. `launch-mistake-capture.vbs` is the silent entrypoint, and
  `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\Journal Mistake
  Capture.lnk` runs it at login.
- The date is resolved at submit time, not at launch — the process runs for days.
- Only `what` is required, and hiding never clears the boxes, so Esc cannot lose
  typing.
- There is no hide-on-deactivate. If the foreground grab loses a race the window
  would vanish the instant it appeared and the hotkey would look dead.
- Forms pixel coordinates are converted to WPF units with
  `Get-DeviceToDipScale` (`Screen.PrimaryScreen.Bounds.Width /
  SystemParameters.PrimaryScreenWidth`, both read in-process). `Graphics.DpiX`
  is wrong for this: it reports monitor DPI even when Forms is already handing
  back virtualized coordinates.
- Only one listener may run; a named mutex makes extra copies exit rather than
  silently fail to take the hotkey.

### Never let the client adopt a revision without the data

`POST /api/mistakes` means the server is now a writer of entry state, which the
browser is not the only source of. `GET /api/tasks` therefore returns `mistakes`
alongside `tasks`, and `syncTasksFromDisk()` merges them **before** adopting
`_revision`.

This ordering is load-bearing and was found the hard way: adopting the newer
revision without the mistakes made the entry stop looking stale, so the next
whole-entry save skipped the 409 merge path entirely and overwrote the captured
rows with the client's empty array. Real rows were lost this way. If any future
field gains a server-side writer, it must ride the same payload — or the client
must not take the revision.

The merge is append-only and honours `removedMistakeIds`, so a poll cannot
resurrect a row deleted in the app while its save is still in flight.

Note that reloading matters after changing this: a browser window still running
older `app.js` will keep clobbering, because the safeguard lives client-side.

### The general case: the rest-of-entry fingerprint

Carrying `mistakes` fixed the one field that had a server-side writer, but the
rule above ("or the client must not take the revision") was never enforced for
anything else. It bit exactly as predicted once the phone PWA meant two clients
were routinely open at once: the phone wrote `night.survey.naps`, the desktop
poll adopted that revision while merging only tasks and mistakes, and the
desktop's next whole-entry save skipped the 409 merge and blanked it. The
oscillation is visible in `entries/.history/2026-07-29/` around r211→r212 and
r225→r226.

`GET /api/tasks` now also returns `restFingerprint`: a hash of the entry with
`tasks`, `mistakes`, `_revision` and `_savedAt` removed — that is, everything the
payload cannot carry. `syncTasksFromDisk()` adopts the revision **only** when
that still matches the base snapshot of what this client last knew the server
held. Otherwise it stays stale on purpose, and the save takes the 409 path where
`mergeEntryVersions()` correctly keeps the remote value for any field this client
never touched.

Details that matter:

- It is compared against `entryBaseSnapshots.get(date)`, **not** the live entry.
  Comparing the live entry would make any unsaved local edit look like a remote
  change and the revision would never be adopted again.
- `stableStringify()` sorts keys, because the two sides build entries
  independently and plain `JSON.stringify` differs on insertion order alone.
  The two copies — one in `app.js`, one in `server.cjs` — must stay identical;
  `tests/entry-sync.test.js` asserts they agree and replays the `naps` loss.
- Excluding `tasks` and `mistakes` is what keeps the common case cheap: a poll
  that only changed those still adopts the revision, so ordinary task edits and
  externally captured mistakes do not generate 409s.
- The client half is sufficient on its own. Against a server that does not send
  `restFingerprint` the client simply never adopts a revision, which is safe but
  takes the merge path more often — so a stale server degrades correctness-first,
  not data-loss-first.

### A failing save must never wedge, and the poll must never overwrite tasks

Staying stale on purpose is only safe if the 409 path can always get out again.
It could not. `mergeEntryVersions()` reported a conflict for any leaf both sides
had changed, `performEntrySave()` gave up on it, and neither `_revision` nor the
base snapshot advanced — so every later save from that window 409'd on the same
leaf forever. Nothing that window did could reach disk again. Meanwhile
`syncTasksFromDisk()` assigned the disk copy over `entry.tasks` outright, so
`TASK_SYNC_DEFER_MS` after adding a task the poll replaced the list with a disk
copy that had never received it. Together those two produced "tasks keep getting
removed from Do right now": the wedge guaranteed the save could not land, and the
poll then deleted the task from memory. Visible in
`entries/.conflicts/2026-07-30/` as 50 consecutive `stale-r50` rejections, which
also stranded that morning's whole survey.

Three rules now hold, all asserted in `tests/entry-sync.test.js`:

- **Tasks merge, they are never assigned.** `mergeTasksFromServer()` reconciles
  base vs local vs disk per section by task id. The base is load-bearing: only it
  distinguishes a task added here since the last successful save (keep) from one
  the HUD has since completed (drop). Disk order wins for tasks both sides know,
  because a reorder has no per-task marker and the HUD reads the first `rightNow`
  row; a locally added task keeps the position the user gave it.
- **A keystroke continuation is not a conflict.** When one side's string extends
  the other's, it is one sentence caught at two keystrokes — the phone saving
  `"Song: X -- "` while the desktop had typed `"Song: X -- Make Sure…"` — so the
  longer string wins and nothing is lost. This resolves the common two-writer
  case outright.
- **A genuinely divergent leaf still resolves, disk-side.** `performEntrySave()`
  re-runs the same merge with local and remote swapped, which yields the disk
  value for those leaves and lets the retry through. Disk must win, not local:
  two windows that each kept their own would overwrite each other indefinitely.
  It is not silent — the rejected attempt is in `entries/.conflicts/`, and the
  save status names the field.

Do not "simplify" the poll back to `entry.tasks = nextTasks`, and do not make a
conflict abort the save again. Both are data loss with a delay on them.

## Eye Rest (Ctrl+Alt+E)

`eyerest-capture.ps1` is a background WPF listener, the same shape as
`mistake-capture.ps1`: no visible window until the hotkey fires. It tries
Ctrl+Alt+E first and falls through a small fallback list (Ctrl+Alt+R,
Ctrl+Shift+Alt+E, Ctrl+Alt+Y) if something else already owns it, showing a
one-time message box naming whichever combo actually registered.

- `launch-eyerest-capture.ps1` starts the local server if needed, then the
  listener. `launch-eyerest-capture.vbs` is the silent entrypoint, and
  `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\Journal Eye
  Rest.lnk` runs it at login, mirroring the mistake-capture shortcut.
- First press starts a session (`sessionStart = Get-Date`) and shows a
  countdown from `sessionDurationSeconds` (default 5:15, editable via the
  Length box, persisted to `eyerest-settings.json`). The countdown is display
  only; a `Done` click stamps `sessionEnd` from the real wall clock, so the
  logged duration is however long the break actually was, not the countdown
  target - that's the "invisible stopwatch."
- `assets/eyerest-gong.wav` is a synthesized single gong strike (inharmonic
  decaying sine partials, generated with a throwaway Node script - not a real
  recording) that plays once when the countdown reaches zero. `$script:gongPlayed`
  guards it from re-firing on every later tick while `remaining` sits at 0;
  `Play()` is async so it never blocks the tick loop even while the window is
  hidden. Editing the Length box re-arms it (`$script:gongPlayed = $false`),
  so shrinking below the elapsed time rings it immediately and growing it back
  past a rung zero lets it ring again at the new target.
- The running panel carries a **blind journaling** box, focused the moment the
  window appears (the Length box no longer takes first focus - the window is
  meant to be typed into with the eyes shut, and editing the countdown length
  is a rare, deliberate click). Plain Enter is a newline inside it, so
  Ctrl+Enter is what finishes the break: once in `running` to stop the clock,
  once in `review` to log it.
- A **focus watchdog** (300ms `DispatcherTimer`) guards the running panel:
  keyboard input goes to the foreground window, so a notification or an app
  stealing the foreground mid-break used to send eyes-shut typing somewhere
  else with no visible sign (once for six minutes straight). While
  `sessionState` is `running` and the window is visible, any tick where
  `GetForegroundWindow()` is not the capture window beeps
  (`SystemSounds.Exclamation`, throttled to one per 2s - sound is the only
  channel that reaches shut eyes), grabs the foreground back with
  `ForceForeground()` (plain `SetForegroundWindow`, then the
  `AttachThreadInput` escalation, then a synthesized ALT tap - Windows refuses
  foreground changes from background processes without them), re-focuses the
  journal box, and records the theft time in the running status line for the
  eyes to find later. Leaving the window deliberately is what Esc (hide) is
  for - hiding stops the watchdog; the review panel is eyes-open and is not
  guarded. The initial `Show-EyeRestWindow` grab uses `ForceForeground` too,
  so a lost activation race at show time is corrected within a tick instead of
  staying silently unfocused.
- The journal box is also written to **`eyerest-draft.txt`** (3s dirty-flag
  timer) as crash insurance, deleted only after a successful submit. A
  `Discard` click with text in the box parks it in
  `eyerest-draft-discarded.txt` (overwritten per discard) instead of erasing
  it, so a slipped click cannot destroy a break's writing. Drafts are never
  auto-restored - they are manual-recovery files, nothing reads them.
- The exported timestamps are the real **writing** window, not the break's:
  `writingStart` is stamped on the first keystroke and `writingEnd` moves with
  every later one (`JournalBox.Add_TextChanged`, ignoring an empty box so the
  programmatic clear in `Start-EyeRestSession` cannot open a window nobody
  typed in). Emptying the box does not reset the start.
- On `Done`, text in the box auto-ticks the "Blind journaling" checkbox - the
  words are their own proof of how the eyes were rested - and the review panel
  says which writing window is about to be exported.
- `Submit-EyeRest` therefore does up to **two** POSTs: `/api/quick-journal`
  (with `title: "Blind journaling"` and `date` = the local day the *writing*
  began, so a break running past midnight lands in the document it started in),
  then `/api/eyerest`. `$script:journalExported` / `$script:restLogged` record
  which half already landed, so a retry after a mid-sequence failure re-sends
  only the missing one - neither the calendar event nor the journal block can
  be written twice.
- Esc **hides**, never discards: the point of the break is not looking at the
  screen, so the countdown/stopwatch keep running with the window hidden.
  Pressing the hotkey again re-shows whichever stage the session is at
  (`sessionState`: `idle` / `running` / `review`) instead of starting a new
  one. A `Discard` button is the only way to actually cancel a session.
- After `Done`, the review panel asks how the eyes were rested: four
  checkboxes (closed eyes and meditated, blind journaling, sat and looked
  around, walked and looked around - multi-select, not mutually exclusive)
  plus a free-text box. At least one checkbox or the text box is required,
  same "don't let an empty submission through" rule as the mistake capture's
  `what` field.
- `POST /api/eyerest` does two writes server-side: it appends an `actual`,
  category-`H` calendar event (title "Eye rest", notes = the selected labels
  and free text joined with `; `) via `queueCalendarEventAppend`, and appends
  a full-precision row (`startedAt`, `endedAt`, `durationSeconds`, `restTypes`,
  `note`) to `eyerest-log.json` via `queueEyeRestLogAppend`. Both are
  chained-promise read-modify-writes, the same pattern as
  `queueGoalLogAppend`, so two sessions logged back to back cannot clobber
  each other.
- When `restTypes` includes `"Blind journaling"` (the string is the contract
  between the checkbox label in `eyerest-capture.ps1` and
  `BLIND_JOURNALING_LABEL` in `server.cjs`), the endpoint does two more things:
  - Appends a **second** `actual` category-`H` event titled "Blind journaling",
    spanning the whole session rather than the keystroke window that
    `/api/quick-journal` timestamps the written block with. The break is the
    sitting; pauses between sentences are part of doing it. It deliberately
    overlaps the "Eye rest" event - the calendar is meant to show how many
    minutes of blind journaling there were, not just that a break happened.
  - Ticks the daily **Journaling** habit for that date
    (`completeJournalingGoalTask`): moves the goal's task into
    `entry.tasks.completed` and appends a `check` goal event with
    `source: "eyerest"`. The goal is resolved from `goals.json` by id
    (`daily-journaling`), falling back to a daily `surface: "task"` goal named
    "Journaling", so renaming it in the app does not silently break this.
    The `check` event matters as much as the completed task: the monthly review
    counts goal-log rows, which is also why `app.js` `completeTask` logs one.
  - If the browser has not been open yet that day the goal never materialised,
    so there is no row to tick. The completed task is written straight in and a
    `materialize` event logged alongside the check - that event is
    `ensureDailyGoalTasks`'s duplicate guard, so without it the app would later
    add an unchecked copy of a habit that is already done.
  - All of it is idempotent: a second blind-journaling break the same day finds
    the check already booked and the task already in `completed`, and only the
    calendar event is appended again.
- `eyerest-log.json` is deliberately not surfaced in the main UI (per the
  design note in the calendar-events request: a running list "somewhere that
  won't overcrowd the UI"). It exists so a future Trends card can read
  session frequency/duration without touching `state.entries`.
- Known gap shared with the rest of `calendar-events.json`: this endpoint's
  read-modify-write only protects against two eye-rest sessions racing each
  other, not against the browser's own full-array `POST /api/calendar-events`
  (`saveCalendarEvents()`) landing in the same instant from an open Calendar
  view edit. That race already existed before this feature; calendar events
  have no per-write revision the way entries do.

## Quick Journal (Ctrl+Alt+Q)

`quick-journal-capture.ps1` is a background WPF listener, the same shape as
`mistake-capture.ps1` and `eyerest-capture.ps1`. It tries Ctrl+Alt+Q first and
falls through a fallback list (Ctrl+Alt+J, Ctrl+Shift+Alt+Q, Ctrl+Alt+U) if
something else already owns it, naming whichever combo actually registered in
a one-time message box.

- `launch-quick-journal-capture.ps1` starts the local server if needed, then
  the listener. `launch-quick-journal-capture.vbs` is the silent entrypoint,
  and `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\Journal Quick
  Journal.lnk` runs it at login, mirroring the other two capture shortcuts.
- First press starts a session (`sessionStart = Get-Date`) and shows one big
  write box - no fields, no choices, just text, so there is nothing between
  having an idea and typing it. `Done` (or Ctrl+Enter) stamps `endedAt` from
  the real wall clock and posts both timestamps plus the full text.
- Esc **hides**, never discards, matching the other two capture tools: an idea
  half-typed must survive an accidental Esc. Pressing the hotkey again
  re-shows the same draft with its original `sessionStart` intact rather than
  starting a new one. `Discard` is the only way to actually clear it.
- `POST /api/quick-journal` appends straight into the day's Document view
  instead of a separate log - the goal is "open the document later and it's
  already there," not another place to check. It takes an optional `title`,
  which prefixes the label as `Title: time - time` (only eye rest sends one,
  `"Blind journaling"`; quick journal itself omits it and keeps the bare time
  range it has always written). It writes `entry.journalHtml`
  directly (`<p><strong>time - time</strong></p>` label, then one `<p>` per
  blank-line-separated paragraph, `<br>` for line breaks within one, `<hr>`
  between successive quick-journal blocks in the same day) and keeps
  `entry.journal` - the plain-text mirror `docPlainText()` normally rebuilds
  client-side, see Document View Formatting above - in sync by hand with the
  same block-per-line convention. Only `P`/`STRONG`/`BR`/`HR` are used, all on
  `DOC_ALLOWED_TAGS`, so `sanitizeDocHtml()` passes the block through
  unchanged the next time the editor loads it.
- This is a server-side writer of `journalHtml`/`journal` with no carry-path
  the way `mistakes` rides `GET /api/tasks` (see "Never let the client adopt a
  revision without the data" above). The entry-sync fingerprint protects the
  common case - a browser window with the Document view merely open picks up
  the appended text on its next poll/save instead of clobbering it. The
  formerly unprotected case - a window holding an **unsaved, in-progress edit
  to the document itself** at the exact moment a quick-journal note lands - is
  now closed by `journalAppendMerge()` in `mergeEntryVersions()`: when one side
  of the `journalHtml`/`journal` leaf is exactly base-plus-appended-suffix, the
  suffix is carried onto the other side's edit instead of the divergent-leaf
  rule taking the disk copy over what was being typed. Journal leaves **only**
  - gluing one side's tail onto the other for any other field would fabricate
  an answer nobody wrote. `tests/entry-sync.test.js` replays this case; run it
  after touching the merge.

## CBT Thought Record (Ctrl+Alt+C)

`cbt-capture.ps1` is a background WPF listener, the same shape as the other
four capture tools. It tries Ctrl+Alt+C first and falls through a fallback list
(Ctrl+Shift+Alt+C, Ctrl+Alt+G, Ctrl+Alt+K), naming whichever combo actually
registered in a one-time message box. None of those collide with the combos the
other listeners try (Q/J/U, W, E/R/Y, L/B/N).

The reason it exists is in the review history: CBT was graded −4, −2, −1 across
three months with the note *"I've kind of forgotten how to do that. I need to
get the template back."* The missing ingredient was the artifact, not the
willpower — this window is the artifact, which is why the form is the Daily
Mood Log out of Burns' *The Feeling Good Handbook*, in the book's order, rather
than a shortened version of it.

- `launch-cbt-capture.ps1` starts the local server if needed, then the
  listener. `launch-cbt-capture.vbs` is the silent entrypoint, and
  `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\Journal Thought
  Record.lnk` runs it at login, mirroring the other capture shortcuts.
- The four steps, as the book has them:
  1. **Upsetting event.**
  2. **Emotions** — the Handbook's nine emotion families plus one free-text
     `Other` row, each scored 0-100% `Now` and again `After`. Families rather
     than single words on purpose: "inferior, worthless, inadequate" is one
     dial, and scoring the family is what stops the log turning into a
     thesaurus exercise.
  3. **Negative thoughts** — up to three cards, each with a `Now`/`After`
     belief rating, the ten distortions as toggle chips (mind reading and
     fortune telling split out of "jumping to conclusions" the way the book's
     own worksheets list them, so eleven chips, each with its definition on
     hover), a positive/rational response, and a belief rating for that.
     Cards two and three start collapsed behind `+ Add another thought`: the
     book wants every thought on the page, but an empty three-card wall is what
     gets the window closed again.
  4. **Outcome.**
- **Only the upsetting event and the first negative thought are required** —
  half a mood log beats none, the same philosophy as the mistake capture's
  `what`-only rule. Do not add validation that requires the rest, and in
  particular do not require the percentages: the before/after numbers are the
  measurement the book is built around, but a record carrying none of them is
  still a record.
- A blank percentage box and one holding `0` are different answers.
  `Get-PercentValue` returns `$null` for anything unparseable instead of zero,
  and an emotion family with neither number is left out of the write entirely
  rather than written as a blank.
- The emotion rows and the thought cards are built in PowerShell from
  `$script:emotionGroups` and `$script:distortions`, not written out in XAML:
  nine rows and three near-identical cards of markup would mean editing one
  label in eleven places. All the colour stays in the XAML styles, so the
  builders only ever set `Style` plus content.
- The body is a `ScrollViewer` whose `MaxHeight` is set on every show from the
  monitor the pointer is on (`Set-BodyHeight`). The full log is around 1500dip
  of content: it fits a desktop screen and does not fit a laptop at 150%
  scaling, so the height cannot be a constant.
- Esc **hides**, never discards; `Discard` is the only thing that clears the
  draft; a re-shown draft keeps its original `sessionStart`. Same contract as
  the quick-journal window.
- Submit POSTs `/api/quick-journal` with `title: "Thought record"` and labelled
  paragraphs — `Upsetting event: …`, the emotion table as one paragraph of
  `family: 80% -> 20%` lines, then one paragraph per thought holding its belief
  line, its distortions and its answer, then `Outcome: …`. Empty sections are
  omitted rather than sent as bare labels. So the record lands in that day's
  Document view exactly like the eye-rest blind-journaling blocks — no new
  server code, no new storage. Single newlines inside a paragraph survive as
  `<br>`, which is what keeps a thought together as one block. The `date` is
  the local day the record was *started*, so one begun at 23:55 files under the
  day that produced the thought.
- The old known race (a server-side append landing during an unsaved document
  edit) is closed by `journalAppendMerge()` — see the Quick Journal section.
  This window is why it had to be: a thought record is the last thing that
  should lose to a merge.
- Nothing reads these records back yet. They are prose inside a day's document,
  so there is no view that tallies which distortions recur or graphs the
  before/after drop, and no chart of any of it. That is the obvious next build,
  and it is why the labels above are worth keeping stable.

## Spotify listening log

Built 2026-09-10. Logs what Spotify says was played into `spotify-listens.json`.
Setup is the same shape as the calendars (own app at
developer.spotify.com/dashboard, client ID + secret pasted into Settings,
OAuth in a popup, tokens only on this machine) and the Settings panel reuses
the `google-calendar-*` classes. The differences that matter:

- **The sync is a server timer, not a button.** `startSpotifyPoller()` runs
  once the port answers and every 10 minutes after (`SPOTIFY_POLL_MS`).
  Spotify's `/me/player/recently-played` returns at most the last 50 plays and
  nothing older, so anything not pulled within roughly 2.5 hours of a long
  session is gone for good. If the journal server is down, those plays are
  lost; there is no way to backfill from Spotify.
- **Idempotent merge.** Every poll re-reads the same 50, so rows are keyed
  `playedAt:trackId` and `mergeSpotifyListens()` drops what is already on
  disk. The `after` cursor (last stored `playedAt`) is an optimisation only.
  A track played twice is two rows; the same play seen twice is one.
- **Nothing is written to Spotify.** Scopes are `user-read-recently-played`
  and `user-read-currently-playing`; the second only feeds the "Now playing"
  line in the panel and is ignored when it fails.
- **Failures park, they do not throw.** A failed poll writes `lastError` to
  `spotify-auth.json` and the panel shows it. An `invalid_grant` on refresh
  sets `needsReconnect` and the timer skips until the account is reconnected;
  the panel badge reads "Needs reconnect".
- **Redirect URI must be `http://127.0.0.1:8787/api/spotify/oauth/callback`.**
  Spotify refuses `localhost` outright. The client credentials go to the token
  endpoint as HTTP Basic, not form fields (Google takes them as fields).
- **Nothing reads the log yet.** No view, chart or survey field consumes it;
  `GET /api/spotify/listens` is the read hook for whatever comes next
  (a "what was playing" strip on the day, a monthly artist tally, mood vs
  music). `playedAt` is UTC; the `?date=` filter uses the server's local day,
  not `timezone-history.json`, so a cross-zone analysis should take `from`/`to`
  instants and localise itself.
- **Server restart required** after editing any of it; app.js only holds the
  settings panel.

## Goals

Goal definitions live in `goals.json`; check-ins live in `goal-log.json`. Design
rationale and the full August 2026 rollout plan are in `GOALS_PLAN.md`.

### Goal state never touches entries/*.json

This is the load-bearing invariant. Goal data is cross-day config plus an
append-only event log, both served by their own endpoints (`/api/goals`
GET/POST, `/api/goal-log` GET/POST). It takes **no part in the entry revision
model**, which is what keeps it clear of the data-loss class documented above:
there is no `_revision` to adopt, no 409 merge path, and no `/api/tasks` poll
payload to ride. If you find yourself adding a goal field to `defaultEntry()`,
stop — that reintroduces the exact bug the split was made to avoid.

The one deliberate exception is `survey.rulecheck`, a human-readable mirror of
the night rule ratings written by `syncRuleCheckSummary()` so the ratings appear
in the Survey output tab and the workbook export. It is derived and write-only;
never read it back as authority. `goal-log.json` is the source of truth.

### Daily goals surface three ways

Each `type: "daily"` goal carries a `surface`:

- `task` — materialised into `tasks.inbox` once per day by `ensureDailyGoalTasks()`,
  carrying `goalId`, `project: "goal"` and an `expiresOn` of that day. Completing
  it logs a `check` against the goal, so the monthly review counts real days.
  **`goalId` and `expiresOn` had to be added to `normalizeTask()` in both `app.js`
  and `server.cjs`** — that function builds a fixed key set, so a field missing
  from either copy is silently dropped.
- `survey` — a checkbox in the night survey's `dailyGoals` block.
- `derived` — already measured by a question the survey has asked for months
  (a habit that one of the `mental` sliders already rates, say). No new
  input; the night block shows these as a read-only readout instead of asking again.

`surface` says where the goal is *asked*, which is not the same as where it is
*answered*. Seven of these are answered from the entry, the calendar or the
eye-rest log whatever their surface — see "The entry answers a daily goal; the
tick is only a shortcut" below. `dailyGoalsWithSurface("derived", …)` still has
no caller: derived goals have no UI of their own, and the evidence table is what
actually gives them outcomes.

As of 2026-08-07 **no daily goal uses `surface: "survey"`** — both checkboxes
were removed, so the night survey's `dailyGoals` block renders only the
read-only task readout. The surface is still supported and `appendDailyGoalsControl()`
handles an empty `checkable` list; nothing needs deleting if a future goal wants
a checkbox again.

Habits are deliberately **not** in the HUD. Only the rule of the day rides there.

A goal task also re-reads its `taskText` and `estimateMinutes` on every pass, so
renaming or re-estimating a goal reaches the row already sitting in today's list
instead of waiting for tomorrow. A goal's `calendarCategory` (the calendar letter
its block is filed under — `15 LinkedIn points` is `B`) is copied the same way,
except that it only fills a blank, because that field is also settable per row.
See "Estimates and placing a task on the calendar".

### Daily goal tasks expire; they do not carry forward

`inbox` carries forward by design, which is wrong for a habit: four missed days
became twenty undated rows and the real todo list was buried. So a materialised
daily-goal task carries `expiresOn` (the day it is for) and
`expireDailyGoalTasks()` sweeps every earlier day at load and at date rollover —
the row is moved to that day's `discarded` and a `miss` is booked against the
date it was for, not the date the sweep ran. `taskExpiryDate()` falls back to the
goal definition when `expiresOn` is absent, which is what cleared the tasks
already on disk from before the field existed and what keeps the sweep correct if
an older `server.cjs` strips the field on save.

Expiry is the **default** for `surface: "task"` daily goals; a goal opts out with
`"expires": false`. That direction is deliberate — forgetting the flag on a new
goal should produce a task that disappears on time, not another silent pile.
A `miss` is skipped when the day already has a `check`, so the survey checkbox
and the task never double-count. Restoring an expired task from history re-dates
it to today, or the next sweep would take it straight back.

The duplicate guard is a `materialize` event per (goal, date). Note the failure
mode this already caused once: `normalizeGoalEvent()` coerces an unrecognised
`kind` to `"check"`, so leaving `materialize` out of `goalEventKinds` did not
error — it booked every habit as completed and re-created the tasks on every
reload. Any new event kind must be added to that set.

### The entry answers a daily goal; the tick is only a shortcut

The expiry sweep above books a `miss` from the state of the *task row*, which
made the log contradict the entry sitting next to it. Through August 2026 the
morning survey was filled in on 19 of 22 days and the log read 2 checks and 4
misses, because the row expired unticked at 16:00 while the answered survey was
right there in `entries/*.json`. Journaling read 30% against a real 68%, the
night survey 17% against 64%. `daily-eye-rest` had the opposite bias — the
checkbox only ever wrote successes, so it read a clean 100% off 13 rows.

`dailyGoalEvidence` in `server.cjs` closes both directions. It maps a goal id to
a rule returning **true** (did it), **false** (demonstrably did not) or **null**
(this day holds no evidence either way). `null` must never become a miss: that
is the same lie pointing the other way, and the `unanswered` kind already exists
for exactly this.

| goal | evidence |
|---|---|
| `daily-morning-survey` | any real answer in `morning.survey` |
| `daily-night-survey` | any real answer in `night.survey` |
| `daily-journaling` | `journal` holds ≥ `journalMinWords` (20) words |
| `daily-eye-rest` | ≥ `eyeRestMinSessions` (5) sessions that date in `eyerest-log.json` |
| `daily-qual-hours` | ≥ `hoursLoggedMinMinutes` (16h) of the day covered by **titled** `actual` calendar events |
| `daily-quant-hours` | the same, for events carrying a **category** |

`surveyHasAnswer()` is the fiddly one. An untouched slider block still carries
every label (`"How much joy?: ; Did I get done what I needed to today?: "`), so "non-empty string" is not
"answered" — at least one label has to have a value after its colon. It also
skips `_`-prefixed autofill flags and the `rulecheck`/`dailycheck` mirrors, or
rating a rule would masquerade as having filled in the night survey.

**Both hours goals read the calendar, not `entry.hours`.** That grid has been
empty on every single day since well before the goals went live, while the same
days carry 6–23 hours of `actual` events — scoring the grid would have booked a
miss on every date and called it data. Qualitative is "writing out what I did"
(the event has a title); quantitative is "the categories like work and travel and
sleep" (the event has a category). They are genuinely different questions:
2026-08-02 was described for 22.6 hours and categorised for only 15.9, so it
passes one and fails the other.

`coveredActualMinutes()` **merges** overlapping spans rather than summing
durations. This is not defensive coding: an eye rest and the blind journaling
inside it deliberately overlap (see the `/api/eyerest` notes), so a summing
implementation would credit a day with hours it never logged.

`eyeRestMinSessions` is the weakest rule here and should be read with that in
mind. The goal is "rest 5 minutes every 30 while working", which the session log
cannot actually confirm; a count is a proxy. Five is not arbitrary — it is the
threshold that reproduces all three answers given by hand before the checkbox was
removed (5 sessions → yes, 4 → no, 1 → no) — but a green day here means "took a
normal number of breaks", not "held the habit". Tying it to logged work hours
instead would be the real fix.

Goals **absent** from the table keep the old semantics exactly. Anki, LinkedIn,
Chinese reading and the day plan leave no trace anywhere but the tick, so for
them the expiring task genuinely is the answer. `daily-protein` is deliberately
unmapped rather than guessed: `eating` records calories, not protein, so there is
nothing to read. It books `unanswered`, which is an honest hole. Wiring a goal up
is adding a row to the table and a case to `tests/goal-evidence.test.js`; nothing
else changes.

Three call sites:

- `saveEntry()` runs `settleEvidenceGoals(date)` after the write, so filling in a
  survey books the check immediately and from any surface — phone capture views
  and the HUD included. It only ever writes checks: during the day, a survey that
  is not filled in yet is not a miss, it is simply not filled in yet.
- `POST /api/eyerest` runs it too, so a break is itself the answer to the
  eye-rest habit.
- `settleEvidenceGoalBacklog()` runs at startup and hourly, **before**
  `finalizeUnansweredGoalDays()`, over every day from the earliest `activeFrom`
  to the backlog-grace edge. This is the one that writes misses, and running it
  first is what stops the unanswered sweep filing a hole against a goal the
  journal already answered.

`machineGoalSources` (`task`, `rollup`, `evidence`) is the safety boundary: the
sweep may revise an outcome it wrote itself, and never one the user entered on a
surface (`app`, `hud`, `eyerest`). That is what let the historical false misses
be corrected without overwriting a deliberate tick — and it is load-bearing in
the other direction too. The eye-rest checkbox was unticked by hand on days when
`eyerest-log.json` shows sessions; taking four breaks is not the same as hitting
"every 30 minutes", so the human "no" stands and the evidence does not overrule
it.

The expiry sweep in `app.js` follows the same evidence: a task whose goal already
has a `check` moves to `completed`, stamped with the check's `ts`, instead of
`discarded`. Leaving it discarded is what made the task history and the goal log
disagree in the first place.

The historical correction was applied on 2026-08-07 by posting the sweep's own
output to `/api/goal-log`; `backups/goal-log.pre-evidence-fix.json` is the log as
it stood before. Nothing was rewritten — the corrections are newer rows, which
is why the reader contract below matters.

### Dropping a goal

Three daily goals changed shape on 2026-08-07, and the mechanics differ:

- `daily-eye-rest` moved from `surface: "survey"` to `"derived"`. The night-survey
  checkbox is gone because `eyerest-capture.ps1` now logs every break, so the
  question was being asked twice. The goal is still live and still scored.
- `daily-bed-by-10` and `daily-calendar` are `archived: true` with an `activeTo`
  of 2026-08-06 — abandoned outright, the first as not a real commitment and the
  second as too vague to answer honestly. Their evidence rules were deleted
  along with them rather than left behind scoring nothing.

Archive rather than delete from `goals.json`: `goalAppliesOnDate()` already gates
on `archived`, so the goal stops materialising, stops accruing, and stops being
asked, while its rows stay in `goal-log.json` and the ids in the log still
resolve to a title.

`trendsGoalTallies()` skips archived goals. Dropping a habit is a decision, not a
failure, and a rate that keeps counting it is measuring the decision rather than
the run. If you ever want a "goals I have abandoned" view, the data is all still
there — the filter is one line and deliberately not configurable, because the
default has to be that a dropped goal stops nagging.

### Append-only semantics

Edits append a newer event rather than mutating an older one, so readers must
take the newest event for a `(goalId, date, kind)` — that is what
`latestGoalEvent()` is for, and rating a rule twice in one evening legitimately
leaves two rows. `POST /api/goal-log` skips ids it has already stored, which
makes replaying a queued batch from an offline client idempotent, and writes are
serialised through `queueGoalLogAppend()` so concurrent appends cannot
read-modify-write over each other.

A **counter** must resolve one outcome per `(goalId, date)` before it counts, not
tally every row. `trendsGoalTallies()` used to increment per event, so a day
answered twice — an edited rating, or a false miss the evidence sweep later
corrected — counted as two days, and the superseded miss went on dragging the
rate down forever. It now takes the newest non-`materialize` row per goal-day and
counts that; `materialize` still counts per appearance, because coverage is
asking a different question. Any new reader of `goalLog` has the same obligation.

### Offline writes queue and replay

The GOALS_PLAN Phase 2 queue, built 2026-08-22. Two halves:

- **Goal events.** `logGoalEvent()` queues a row into localStorage
  (`aa-journal-goal-queue-v1`) when the POST fails on a **network error only**
  — a 4xx means the server saw it and said no, and replaying that forever
  would be a different bug. `flushGoalEventQueue()` replays at boot, on the
  `online` event, on the tab becoming visible, and on a 60 s timer while
  anything is queued; `POST /api/goal-log` skips ids it already stored, so a
  replay is idempotent by design. `loadGoalLogFromDisk()` re-appends queued
  rows to the in-memory log after a load, so a reload while offline does not
  show yesterday's tick undone.
- **Entry saves.** A failed disk save used to end at "Saved locally", and a tab
  closed later lost the edit to the startup rule that disk beats localStorage.
  Now the failed dates land in `offlinePendingSaveDates` and
  `retryOfflineEntrySaves()` re-sends them (15 s timer, plus the same
  online/visibility triggers) until the server answers; the revision machinery
  handles whatever happened on disk meanwhile. The status line says
  "retrying when the server is back" so a dead server is visible.

### Capture outbox (the hotkey windows offline), 2026-08-29

The same queue one layer down, for the five PowerShell capture windows. Before
this, every one of them ended a failed POST at "Event Horizon is not running.
Your draft is kept - start it and press Ctrl+Enter again": the capture was held
hostage to a node process the user is not supposed to think about, at the exact
moment they are mid-break with their eyes shut. **The server being down must
never cost a capture and must never hold a window open.**

- `capture-outbox.ps1` is dot-sourced by `quick-journal-capture.ps1`,
  `mistake-capture.ps1`, `learn-capture.ps1`, `cbt-capture.ps1` and
  `eyerest-capture.ps1`. `Invoke-CapturePost` replaces the raw
  `Invoke-RestMethod` in each submit path and returns one of four states:
  `sent`, `queued`, `rejected`, `failed`.
- `queued` means the payload is a file in `outbox/`, and from the window's point
  of view it is identical to `sent`: boxes clear, window closes. It shows
  `$captureQueuedStatus` for 1.5 s first (`Start-CaptureNoticeHide`), because
  closing silently would be indistinguishable from a normal log and the one
  thing the user must know is that this one did not reach the server.
- `rejected` keeps the old behaviour - window open, text intact. Same rule as
  the browser queue above: **queue on a transport failure only.** A reply with
  a status code means the server saw it and said no.
- `failed` is unreachable *and* the outbox could not be written. Nothing is safe
  to close over, so the window keeps everything.
- A window that opens while anything is queued says so in its status line
  (`Format-CaptureStatusWithOutbox`), so a server that has been down for a week
  is visible where the user is already looking.

Server side, `drainCaptureOutbox()` replays `outbox/*.json` in filename order
(the name leads with the queue timestamp, which eye rest depends on - it queues
the blind-journaling block before the break it was written during) by POSTing
each one back to itself over loopback, so replay goes through the real handler
rather than a second copy of it. It runs in the `listen` callback and every five
minutes after. A file is deleted only on `ok`; a 4xx moves it to
`outbox/rejected/` rather than deleting it, and anything else leaves the whole
queue in place for the next attempt. `captureOutboxEndpoints` is the allowlist -
a file on disk must not be a way to reach the rest of the API.

Replay is idempotent through `captureId`. Every payload carries one, the four
capture endpoints check it against `capture-ids.json` (rolling 500) and answer a
repeat with `{ ok: true, duplicate: true }` without writing. That is what makes
it safe to queue a POST that **timed out after the server had already written
it** - the one case no transport error can tell apart from a dead server.
Timestamps ride in the payload, so a capture replayed the next morning keeps the
time it was typed, not the time it landed.

Two things that will bite: PowerShell 5.1's `Set-Content -Encoding UTF8` writes
a BOM and `JSON.parse` refuses it outright, so the outbox writer uses
`[System.IO.File]::WriteAllText` with a BOM-less encoder and the server strips a
leading BOM anyway; and the queue file is written as `.json.tmp` then renamed,
because the drain globs `*.json` and must never read a half-written file.

### Context is date-scheduled, not toggled

`goalsDoc.contextSchedule` maps dates to a context (`travel`, `davis`, `dc`) and
`activeContextOn()` resolves it. A goal whose `contexts` array excludes the
active context is dormant and **must not accrue misses** — the August 2026 case
is gym goals during travel, which took five zeros in the Feb review for a reason
known three weeks in advance. `goalTitleOn()` applies `contextLabels` so one goal
can read "Park calisthenics" while travelling and "Gym session" in Davis.

### Backlog grace

`withinBacklogGrace()` allows today and the previous `backlogGraceDays` (2).
Older days render locked and are never surfaced, counted as owed, or prompted
for; `goalBacklogUnlocked` is the deliberate escape hatch. Future dates are
locked too — check-ins are retrospective. Do not add a "you owe N days" badge:
a growing debt is what killed the survey streaks twice in the review history.

### Rule of the day

`goalsDoc.ruleSchedule` maps every date to a rule id. July and August 2026 were
seeded up front; any later month is generated on first access by
`ensureRuleScheduleForMonth()` and then **persisted via `POST /api/goals`**.

Months are always scheduled whole, never day by day. Allocation is even across
the active rules with the remainder going to the highest `weight` (only
`rule-regret` has one, at 2), then a deterministic shuffle seeded from
`year * 100 + month`, then a pass that breaks adjacent repeats. That makes the
distribution fair by construction — 31 days over 10 rules is three each plus one
— rather than leaving it to chance, and it lets the UI show tomorrow's rule.

Persisting matters for a specific reason: the generation reads the *current*
rule list, so without freezing the result, adding or retiring a rule later would
retroactively change which rule a past day actually displayed, and the monthly
review would be grading against a schedule that never happened.
Surfaces: `.survey-note.rule-of-day` above the morning `ruleplan` question, and
the bespoke `ruleRatings` control (`appendRuleRatingsControl()`) for the night
`rulecheck` question, which rates on the same −5..+5 scale as the monthly review.

The roster is edited in Settings → Rules for life (`rulesForLifePanel()` in
`app.js` — deliberately out of the way, since edits are rare). Renames follow
the rule id everywhere, past days included. Any roster change (add, retire,
restore, weight) calls `rebuildFutureRuleSchedule()`, which deletes schedule
entries strictly after today and re-deals this month's remainder and the next
month — the freeze described above is why edits must never touch dates ≤ today.
Retiring archives the goal (`archived: true`, `activeTo` = today) so history
still resolves its title; outright delete is only offered when
`ruleHasHistory()` says the rule was never shown on a lived day and never rated.

### Hourly alert and night survey reminder

One notification an hour, on the hour (`showHourlyCalendarNotification()`):
"Fill in your last hour" with the hour to log, plus a second line from
`planNowLine()` saying what the plan says to do -- `Now: <block> (until
3:30 PM)` for the plan block(s) under way, else `Next: <block> at 2:30 PM`.
That second line is the "what to do" notification; it rides in the hourly one
rather than firing at the start of every plan block. One ping a night at 21:00
(`scheduleNextNightSurveyReminder()`), gated on the same
`desktopCalendarNotifications` setting. Bed-by-10 and the day's rule ride along
in that one notification body on purpose — three alerts inside an hour is how
notification blindness starts.

**The setting is intent; permission is per browser. Never write one from the
other.** `desktopCalendarNotifications` lives in `app-settings.json` and is
shared by every device that opens the app; `Notification.permission` belongs
to one browser. Until 2026-09-08 the code wrote `false` into the shared setting
whenever a browser lacked permission -- on the first click of a device with
permission still `default` (a phone on the local network, a fresh profile, the
preview pane) and whenever `new Notification()` threw (Android refuses the
page constructor outright). That is how the alerts stopped on the desktop
without anyone turning them off. Now only the toolbar toggle changes the
setting, it records what was asked for before it asks the browser, and a
browser that cannot show the alert says so in the status line (and strikes
through the `Hourly alerts` label, `.is-blocked`) and leaves the setting alone.
`showAppNotification()` is the one place an alert is posted, via the page
`Notification` constructor only. The service-worker fallback for Android went
with the service worker on 2026-09-10 (see "No service worker" below).

**A tab only writes the flag it changed.** The settings file is posted whole on
every save, so a tab that loaded an hour ago used to overwrite a toggle made
since (on the phone, in the preview pane, or in a fresh reload) with the stale
value it had loaded -- which is exactly how the 2026-09-08 fix was undone the
same night: the old tab stayed open until morning and wrote `false` back.
`saveSettingsToDisk()` now re-reads the flag from disk first
(`adoptDesktopAlertsSettingFromDisk()`) unless `desktopCalendarNotificationsOwned`
says this tab's toggle is the pending change; the same re-read runs on
`visibilitychange` and right before each hourly alert decides whether to fire.
Shift+click on a lit `Hourly alerts` button sends the alert immediately
(`sendTestCalendarNotification()`) so "is this working" does not wait for the
top of the hour.

### Serving to a phone

The server binds 127.0.0.1 only. To reach it from a phone, either set
`JOURNAL_HOST=0.0.0.0` on a trusted home network or, better, put a VPN or a
mesh-network reverse proxy in front of the loopback port so the Node server
itself never binds a routable interface. Whatever you use, do not expose it to
the public internet — this server has no auth.

### No service worker

Removed 2026-09-10 and not to come back. `sw.js` used to cache the app shell
network-first as an offline fallback. That fallback let the installed Edge
window boot with the server down: Windows restored the window after a reboot a
few seconds before `launch-journal.ps1` had `server.cjs` listening, every boot
GET failed, and the client sat on compiled-in defaults until the server
answered, then posted them whole over `app-settings.json`. That erased two
entries from a settings list, and the calendar normaliser then blanked the
matching field on the 14 events that named them. The hourly-alert flag had
gone the same way earlier. `index.html` now unregisters
any worker a browser still holds and clears its caches, and `sw.js` is a stub
that unregisters itself. The page must fail to load until the server is there;
that is the only safe behaviour for an app whose files are posted whole.

Two client-side rules came out of the same incident and stay regardless:
`saveSettingsToDisk()` returns early until `settingsLoaded` (settings merged
from disk, with the same retry-until-it-lands as `calendarEventsLoaded`), and
`normalizeCalendarEvent()` keeps an event's own fields verbatim instead of
blanking values missing from a settings list. An event's own data is never
corrected from a settings file. Custom choices, goals and people are still posted whole
with no load gate; without a worker a client cannot boot without the server,
but a load-gate there is the next thing to add if any of them ever regress.

`JOURNAL_HOST=0.0.0.0 node server.cjs` binds all interfaces and logs the LAN
addresses. Loopback remains the default because this server has no auth.

### Desktop left rail

The left pane drags between `LEFT_PANE_MIN` (64) and `LEFT_PANE_MAX` (620) in
`app.js`. Below `LEFT_RAIL_MAX` (170) — the width where "Morning Survey" stops
fitting — `applyPaneSizes()` puts `body.left-rail` on, and the `icon rail`
block in `styles.css` hides `.side-nav-label` and shows the button's inline
`.side-nav-icon` SVG, plus hides the guide head and `#checklist`, which are
unreadable at that width. Labels stay in the DOM and JS never reads or writes
them (same contract as `data-mobile-label`); each button carries a `title` for
the tooltip and the accessible name. The phone block re-hides `.side-nav-icon`
so a rail width persisted from the desktop cannot leak icons into the bottom
tab bar.

The guide panel's document-view body used to be a read-only "Original Plan"
list of the 24 `entry.hours.plan` cells. That was removed as legacy; the plan
data itself is still edited in the hour grid and still ships in the workbook
and markdown exports. In the document view the guide panel is now nav only.

### Phone layout

All of it is one marked "Phone layout" section at the **end** of `styles.css`,
plus `toggleMobileMore()` in `app.js` and two markup hooks in `index.html`
(`#mobileMoreButton`, and `data-mobile-label` on the six side-nav buttons). It
must stay last in the file: the trends and document-editor sections above set
properties it overrides, and on equal specificity the later rule wins.

The media condition is `(max-width: 760px), (max-width: 950px) and
(max-height: 480px)`. The second half is the same phone rotated — at 812x375 the
desktop grid left the writing surface 38px tall and starting below the fold.

What the layout does, and why each piece is load-bearing:

- The shell becomes a fixed-height flex column and `html, body` get
  `overflow: hidden`. Without the root lock the page still gained a scroll range
  on the night survey and the topbar could be dragged off screen: every box was
  correctly clipped, but Chromium propagates a tall `fieldset`'s scrollable
  overflow out to the document. It also stops iOS rubber-banding the app.
- `.side-nav` becomes a fixed bottom tab bar. That works because `.guide-panel`
  goes `display: contents`, which drops its box but keeps its children in the
  layout — a `position: fixed` child of a `display: none` parent renders
  nothing. So do not "simplify" that to `display: none`.
- Nav labels are swapped for `data-mobile-label` via `font-size: 0` plus an
  `::after`. JS only toggles `.active` on those buttons and never reads or
  writes their text, which is what makes this safe.
- `#mobileMoreButton` toggles `body.mobile-more-open`, which reveals the
  desktop-only chrome (colour pickers, day search, guide checklist, export row,
  output panel) and turns the shell into a scroller. It is presentation only —
  not persisted, and it never touches entry state.
- In that mode `.capture-panel` needs an explicit `height`, not `min-height`:
  its work-area row is `minmax(0, 1fr)`, so sizing to content let a long task
  list grow the panel to thousands of pixels and pushed the revealed panels out
  of reach.
- The output panel's `is-collapsed` state is a desktop side-rail (it rotates the
  tab strip vertically down the right edge), so the phone layout forces the
  expanded presentation and hides `.output-toggle`. The inactive tab panels keep
  `.hidden`, which is `!important`, so tab switching still decides what shows.
- `.survey-card` gets `min-inline-size: 0`. A `fieldset` defaults to
  `min-content`, so one wide control inside stretched the whole card — and the
  page — well past 375px.
- **Anything made a horizontal scroller here also needs an explicit
  `min-height`.** A scroll container's min-content height is zero, so as a grid
  item in an auto track it collapses to `0px` and vanishes. That bit the task
  filter bar, and the same applies to the mini row and the output tabs.
- Form controls are pinned to `font-size: 16px`. Below that iOS zooms the page
  on focus and leaves it zoomed.
- The doc toolbar becomes one scrolling row, which means its dropdowns would be
  clipped to its 50px height, so `.doc-menu` goes `position: fixed` and opens as
  a bottom sheet. Only the `.hidden` class toggles those menus and nothing reads
  their geometry, so this stays presentation-only.
- The task row drops `.drag-handle`. The grip is decorative — `row.draggable` is
  what starts a drag, and HTML5 drag events do not fire for touch anyway.

Second wave (2026-08-17), after the calendar turned out to be unusable on the
phone:

- **`.capture-panel` gets an explicit `grid-template-columns: minmax(0, 1fr)`
  and `.work-area` gets `min-width: 0`.** Without them the panel's implicit
  auto column grew to its items' max-content size — the week grid's min-width
  inflated the whole track to ~1180px inside an `overflow: hidden` shell, so
  the days past Tuesday were not awaiting a scroll, they were **clipped and
  unreachable**, and `.editor-head` and the mini row rode along. With the
  column pinned, `#calendarView` (which was always `overflow: auto`) becomes
  the sideways scroller the wide grids assumed existed. `min-width: 0` on the
  item alone is NOT enough: an auto grid track sizes to max-content regardless
  of its items' min-width.
- The week grid drops to `min-width: 800px` with a 44px hour gutter (desktop
  keeps 920/64), and `.calendar-time-axis`/`.calendar-time-zone` go
  `position: sticky; left: 0` with their own background so the clock column
  survives the sideways scroll. Their z-index (8) sits under the sticky-top
  header (10) and over the event blocks.
- The month grid trades its `repeat(7, minmax(96px, 1fr))` floor for
  `minmax(0, 1fr)` plus shorter cells, so a month fits the screen outright —
  sideways scrolling is wrong for the one view whose point is the overview.
  Event chips already clip to their cell and overflow into `+N more`.
- The calendar toolbar and `.top-controls` become one scrolling row each (the
  task-filter-bar pattern, including the load-bearing explicit `min-height`).
  The topbar's second row was all icons and cost 44px of every view. While
  `body.mobile-more-open`, `.top-controls` reverts to wrapping because the
  drawer reveals the search panel and colour pickers inside it and those need
  whole rows.
- The tab bar's columns are `repeat(auto-fit, minmax(56px, 1fr))`, not a fixed
  `repeat(8)`: six tabs show with the lists group folded, ten with it open, and
  hidden buttons make no tracks. A `body:has(.side-nav-group:not(.hidden))`
  rule grows the shell's bottom padding while the second row of tabs is open.
- `.segmented-control button` (including the calendar toolbar's, whose desktop
  rule is more specific and must be out-specificity'd by name) goes to 40px;
  range inputs get `min-height: 28px`; choice checkboxes go 24px.

Third wave (2026-08-22), native-feel polish:

- **Touch basics are global**, near the top of `styles.css`: transparent
  `-webkit-tap-highlight-color`, `touch-action: manipulation` on every control
  (kills the ~350ms double-tap-zoom wait), and `user-select: none` plus
  `-webkit-touch-callout: none` on buttons/summaries so a long-press cannot
  start a selection on chrome.
- **A `@media (hover: none)` "Touch input" section** sits just before the phone
  layout (not width-gated — it covers an iPad too). On touch, `:hover` is
  sticky on the last-tapped control, so it resets the visible hover effects and
  replaces them with instant `:active` press-dims that fade on release. The
  resets use `:not(.active)` / `:not([open])` guards so they never override a
  control's real toggled-state styling — keep that if adding more.
- **The status bar matches the app.** `applyColors()` retargets the
  `theme-color` meta to the current panel colour (custom colours included);
  iOS paints the standalone status bar with it. The phone layout moved the
  safe-area top inset from `.app-shell` onto `.topbar`'s padding so the panel
  colour runs to the screen's top edge like a native nav bar. The manifest and
  the static meta hold the day-theme panel colour for first paint.
- **`setupKeyboardWatcher()` in `app.js`** (called from DOMContentLoaded) flags
  `body.keyboard-open` when `visualViewport` shrinks >120px below
  `window.innerHeight`, and maintains `--vv-top`/`--vv-height` on `:root`. iOS
  never resizes the layout viewport for the keyboard, so without this the fixed
  tab bar floats mid-screen once iOS pans to the focused field. While typing:
  the tab bar hides (`display: none`), the shell's 56px bottom padding drops,
  and `.doc-menu` bottom sheets pin to the *visual* viewport top via the vars
  (their normal anchor is behind the keyboard). The keyboard rules must stay
  after the `body:has(...)` padding rule — equal specificity, order decides.
  Presentation only; it never touches entry state or input focus.
- The tab bar is translucent over a backdrop blur (iOS tab-bar look), with the
  solid `var(--panel)` kept as the declaration above it for browsers without
  `backdrop-filter`.
- Horizontal scroller rows get `overscroll-behavior-x: contain` and the view
  containers/checklist/doc menus `overscroll-behavior: contain`, so running out
  of scroll in a row no longer hands the gesture to what is behind it.

Nothing in the section sets `display` on a `#workArea` view container, and
nothing affects task input focus or blur, so the `syncTasksFromDisk()` typing
guard and the document editor's caret rules are untouched.

## Monthly review

The −5..+5 monthly retrospective that used to live in `New Years Goals
Progress Check-In.xlsx` (four columns: Goal / How well did I do / Explain /
How should I change it for this next month, one ALL-CAPS row per category).
All code sits in one marked "Monthly review" section of `app.js`
(`renderMonthlyReviewView` and the `review*` helpers) plus a section in
`styles.css` and the handlers in `server.cjs`.

- **Entry point is a button in the Trends controls row, deliberately not a nav
  slot.** This is a once-a-month surface; do not add it to the side nav or the
  daily chrome. `activeView === "review"`, `#reviewView` in `index.html`.
- **Every goal row shows the month's evidence before the grade is typed**:
  done/missed/unanswered counts, longest run, last-done date from
  `goal-log.json` (rules add their schedule count and rating average). The
  reader follows the same one-outcome-per-(goal, date), newest-non-materialize
  contract as `trendsGoalTallies()` — see `reviewMonthOutcomes()`. This is the
  entire point of the surface: the review grades the record, not the memory of
  it ("Chinese reading: 11/31 days" instead of "didn't do a great job overall").
- Grades live in `monthly-reviews.json`, month-scoped, serialised writes, no
  part in the entry revision model (the goals rule). **What is saved is the
  month's own row list, never a rebuild from the current goal roster** —
  imported months hold rows no current goal matches, and a rebuild would
  silently drop them. `tests/monthly-review.test.js` pins this.
- Months imported by `tools/import-monthly-reviews.cjs` (Jan–Mar 2026, run
  2026-08-22) carry `imported: true`, keep the sheet's own row order, and
  render editable. Import matched sheet rows to goal ids with a rarity-weighted
  title match (`buildGoalMatcher` in the tool) because goals.json titles are
  rewritten short forms; unmatched rows keep their title alone. Matched rows
  are what feed the "Jan +2 · Feb −4" past-grade chips beside each goal.
- The workbook's fractional grades ("5.0 in Feb") get their exact value as an
  extra select option rather than being rounded or blanked.
- Export: `Copy TSV` (paste into the workbook) and `Download .xlsx` — the
  server wraps client-built sheet rows into a one-sheet workbook via a
  dependency-free stored-zip writer (`buildXlsxWorkbook`/`buildZipArchive`).
  `reviewSheetRows()` is the single source of shape for the view, the TSV and
  the xlsx, so the three cannot disagree.
- Default month flips to the current month from the 25th
  (`defaultReviewMonth()`); before that it is last month, still being finished.
- `renderMonthlyReviewView` has the `renderLearnView` focus-guard contract:
  without `force` it declines to rebuild while one of its inputs has focus.

## Survey Form Panels

Two panels sit above the questions in both surveys, built by `renderSurveyForm()`
in the order edit bar → transfer → calendar → mistake prompt → night evidence.

### Moving a survey onto the day it belongs to

A survey filled in against the wrong date used to cost a full retype, so in
practice the wrong day kept the answers. `appendSurveyTransferPanel()` folds out
of the "Move or copy day…" button next to "Edit survey" and asks two questions:
direction (send this day's survey elsewhere / bring another day's here) and
whether the source keeps a copy.

The transfer is **wholesale, never a merge**. Half of Tuesday's answers over half
of Wednesday's describes a day that never happened, and nothing afterwards could
tell you by eye which half was which. `transferSurvey()` deletes every
transferable key on the target before assigning, and `runSurveyTransfer()` puts
the replaced count behind a `confirm()`.

What travels, and why it matters:

- **`rulecheck` and `dailycheck` never travel.** They are write-only mirrors of
  goal-log rows for their own date (see "Goal state never touches entries"),
  rebuilt on every render of the day that owns them, so carrying them would file
  one day's habits under another's. `SURVEY_TRANSFER_SKIP_KEYS`.
- **The `_`-prefixed autofill markers do travel**, with the answers next to them.
  Without them the sleep and nap prefills would read a moved answer as an
  untouched field and refill it from the *other* day's calendar.
- `checked` moves with `survey`. `surveyFingerprint()` in `server.cjs` already
  treats the pair as one unit, so splitting them here would make a moved survey
  look half-edited to the activity stamp.

Two consequences worth knowing before "the move did not work" gets filed as a
bug. A **move leaves the source blank, and the very next render refills its sleep
and nap answers from that day's own calendar** — the source ends up looking like
a day that was opened but never answered, which is exactly what it now is.
And `surveyActivity` is stamped by the server from the disk copy, so the target
day's `finishedAt` is the transfer, not the original sitting. Moving a survey
repairs the answers, not the record of when they were typed.

Undo is the panel's own button, not Ctrl+Z: `persistRestoredAppHistory()` writes
only the *current* entry back to disk, which would leave the other half of a
cross-day move stale on disk. `undoSurveyTransfer()` restores both days and saves
both. The offer retires itself once the target has been edited by hand —
`record.resultFingerprint` is compared against a fresh
`surveyTransferFingerprint()` on every render. Only the target is fingerprinted;
a source fingerprint would go stale within a frame of the move that made it,
because of the refill above.

`tests/survey-transfer.test.js` extracts the real functions. Run it after
touching `transferSurvey()`, `undoSurveyTransfer()`, `runSurveyTransfer()`,
`surveyAnswerCount()` or `SURVEY_TRANSFER_SKIP_KEYS`. `surveyAnswerIsReal()` is a
deliberate mirror of `surveyValueAnswered()` in `server.cjs` — the same rule
decides whether a day is worth moving here and whether the goal log counts it as
filled in there, and they have to agree.

### The day's calendar inside the form

`appendSurveyDayCalendar()` draws the day as a read-only agenda, `position:
sticky` at the top of `.form-view` so it is still there at question 20. Both
surveys ask what the day was like and most of the answer is already on the
calendar; leaving the form to look it up is what gets a half-filled survey
abandoned.

Read-only is not laziness. The real grid drags, resizes and opens an editor on
pointer events, none of which belongs behind a form being typed into, and its CSS
is written against `.calendar-view` ancestors — reusing `calendarGridDayColumn()`
here would mean dragging that layout along with it. "Open in calendar" is the
escape hatch.

`surveyCalendarKind` is deliberately **not** `calendarKindFilter`: checking what
actually happened while writing the night survey must not silently re-filter the
calendar view. Both it and `surveyCalendarOpen` persist through `appSettings()`.
The summary line reuses `coverageSpans()`/`coveredMinutesWithin()`, so its "Xh
logged" is the same merged-span number the footer counters use rather than a
second, disagreeing sum.

### Auto-detected people in the interaction question

By the time the night list is filled in, the day has been written down twice
already: as `kind: "actual"` calendar blocks and in the daily document. Anyone
named in either is hoisted into an **"Auto-detected today"** group above the
ordinary groups, and the confident matches arrive ticked, with a notice
above the grid naming who was ticked and which source named them. Everything
lives in the marked "Auto-detected people" section of `app.js` plus the block
inside `rebuildGroups()` in `appendInteractionControl()`.

What it reads, and what it refuses to read:

- **Actual blocks only** (title + location + notes), never plans. A block you
  meant to spend with someone is evidence of an intention, not of an evening.
- **`entry.journal`**, the daily document. Not the survey's own free text.
- Matching is whole-word (`mentionsName()`, no lookbehind — this runs on the
  phone) against the person's *display string, registry name and every alias*,
  with number prefixes and `(from class)`-style parentheticals stripped: nobody
  writes "7 Priya" in a sentence. Words under three letters never match bare, so
  a two-letter given name is only found by the full name, and `ma` in "the ma
  and pa shop" is not a mention.

Two rules stop it filing a wrong answer, and both are load-bearing:

- **A shared first name is surfaced but never ticked.** Ambiguity is counted
  over the whole registry *including archived people* — say the user has three
  Jordans and only one is still on the list, and tonight's "Walked around with
  Jordan" belonged to an archived one. Counting only the offered names would
  turn that into a confident, wrong tick. Archived people go into the candidate
  pool flagged `offered: false`: they can create ambiguity and can absorb a
  full-name mention, but are never returned as hits.
- **A name is auto-ticked at most once per day**, recorded in
  `survey._interactionAuto`. Unticking someone the detector got wrong has to
  stick, or the box re-checks itself on the next filter keystroke. The `_`
  prefix keeps the marker out of `surveyAnswerCount()` while still letting it
  travel with a transferred survey, like the other autofill markers.

Detection runs over the **roster**, not the filtered `visible` list. Typing
"jor" in the filter box must not hide the second Jordan and promote an
unresolvable name to a confident tick.

`tests/interaction-detect.test.js` extracts `detectInteractionMentions()`,
`personNameForms()`, `mentionsName()` and the marker helpers by string marker
(`const INTERACTION_AUTO_KEY` → `function appendInteractionControl`). Run it
after touching any of them.

## Question types and writing questions

`SCHEMA.surveys` holds the questions the app shipped with. Anything added by
hand lives in `custom-choices.json` under `customQuestions`, next to the custom
choices, because the two are edited from the same screen and saved by the same
call. `allSurveyQuestions(session)` concatenates the two and applies
`questionOrder`; `visibleSurveyQuestions()` filters that by date.

### The registry

`QUESTION_TYPES` (top of `app.js`) is the single description of every type.
The add-question picker, the Settings toggles and the export formatter all read
it rather than keeping their own lists. Each entry carries:

- **`tier`** — `standard` (always in the picker, 11 of them), `optional` (hidden
  until switched on in Settings → Survey question types, 12 of them), or
  `builtin` (`ruleRatings`, `dailyGoals`, `albumReviews`: they render, but are
  bound to the goal log and the album list, so they can never be a new
  question).
- **`stores`** — the shape of the saved answer, which is the contract the rest
  of the app reads back: `text`, `list` (comma-joined), `pairs`
  (`"Label: value; Label: value"`), `media` (`{ text, image?, files? }`) or
  `none`.
- **`config`** — which extra editor fields the type needs (`choices`, `fields`,
  `scale`, `total`, `tree`, `columns`, `groups`, `body`, `image`, `regions`).

New types render through `SURVEY_CONTROL_RENDERERS`, dispatched from
`appendSurveyControl()` after the four app-specific types and before the
original choice/form/slider blocks. **Every type in the registry that is not
`builtin` needs an entry there** — a type in the picker with no renderer is a
question that can be created and then cannot be answered.

Almost everything stores as `pairs`, on purpose. A matrix, a ranking, a
constant sum and a side-by-side all come out looking like the `form` and
`slider` answers that already existed, so the markdown export, the goal
evidence sweep and `surveyAnswerIsReal()` needed no teaching.

### Effective dating, and the one difference

Adding or removing a question uses the existing `questionHistory` mechanism, so
an edit applies from the current date onward and earlier days keep the survey
they had. The one difference is the default before a question's first event:
`isQuestionVisibleOn()` takes a `defaultVisible`, and `isSurveyQuestionVisibleOn()`
passes `!question.custom`. A shipped question was there all along; a question
written today was not, and defaulting it visible would put an unanswered
question on every day already in the journal — and make those days start
reading as incomplete to the goal sweep.

Reordering is deliberately *not* effective-dated. It carries no answers, so
there is nothing about an earlier day a reorder could falsify.

Only custom questions get an Edit button. The shipped ones are referred to by
id across sleep detection, the goal sweep and the historical import, so a
renamed `sleep` would be a rename in one place and a break in five. A custom
question's id is derived from its label once, at creation, then frozen: the id
is the key answers are filed under, so renaming changes what it says and not
where its history lives.

"Remove question" hides from today onward and is the normal path. "Delete
completely" (inside the editor) drops the question everywhere including the
past, and says so.

### Attachments

`fileUpload`, `audio` and `video` store `{ text, files: [] }` — the same `text`
key `textImage` already used, extended with a file list. `signature` stores a
PNG through the existing `/api/survey-image`.

`/api/survey-file` is separate from `saveSurveyImage()` rather than a loosening
of it: that one re-encodes and caps at 4 MB because it feeds an `<img>`. The
file endpoint caps at 25 MB, keys extensions off the **declared mime type
only** (never the uploaded filename), and rejects anything outside
`SURVEY_FILE_EXTENSIONS` with a 415.

Two traps, both already sprung and fixed:

- MediaRecorder reports `audio/webm;codecs=opus`, so the data-URL regex has to
  match and discard parameters. Rejecting them would fail every in-app
  recording while file picks kept working.
- Audio-only WebM is stored as `.weba` so `contentTypes` can serve it as
  `audio/webm`. Served as `application/octet-stream` — or as `video/webm` — a
  recording uploads fine and then will not play back.

`surveyValueAnswered()` in `server.cjs` and `surveyAnswerIsReal()` in `app.js`
both had to learn `files`, or a voice note with nothing typed beside it would
read as an unanswered question. They are mirrors and must stay one;
`tests/survey-transfer.test.js` covers the client half.

## Sleep Detection From Calendar

Category-Z `kind: "actual"` calendar events are the raw sleep record. Two survey
surfaces read them (all in the marked "Sleep detection from calendar" section of
`app.js`):

- Morning survey `sleep` question: `appendSleepDetectionNote()` shows what the
  calendar says (fell asleep, final wake-up, mid-sleep wake-ups, time awake) and
  prefills "Time I fell asleep" / "Time I woke up" / the `awake` question. A
  "Use calendar times" button re-applies on demand.
- Night survey `naps` question: `detectNapsForDate()` auto-fills daytime sleep
  blocks, and a "Calendar also shows" note offers to add ones logged later.
  Missing-nap matching is by time overlap, not exact equality, so a
  hand-adjusted nap does not keep re-listing its calendar twin.

Night vs nap (`detectNightSleep()`): merged Z-actual blocks from noon the day
before through the survey day; the core is the longest block (>= 90 min) whose
midpoint falls between previous-day 18:00 and survey-day 12:00; neighbors chain
into the night only when the waking gap is <= 180 min AND the sleep on the far
side lasted at least as long as the gap. That is what makes 19:00-03:00 + an
hour awake + 04:00-08:00 one night with one wake-up, while waking at 08:00 then
napping 09:00-09:30 stays a nap. Naps for a date exclude both the night that
ended that morning and the night starting that evening (which belongs to the
next day's morning survey).

Prefill is once per day and only into empty fields: `_sleepCalendarAutofill` /
`_napsCalendarAutofill` markers on the survey object keep a deliberately
cleared answer from being refilled on every render. Those `_`-prefixed keys are
invisible to outputs/Missing (both iterate SCHEMA questions), so do not add a
question id starting with `_`. Detection reads only `state.calendarEvents` via
`eventsForDay()`; plan events and non-Z categories are ignored.

`tests/sleep-detect.test.js` (run with `node tests/sleep-detect.test.js`)
extracts the real detection functions from `app.js` and runs the night/nap
scenarios against synthetic events. Run it after touching the detection section.

## Time zones

Added after a move between time zones made the year's hour totals quietly
wrong.

**The principle: never convert stored data; record the zone at write time; derive
dates at write time, not read time.** Journal hour lines, calendar `start`/`end`
(naive `YYYY-MM-DDTHH:MM`) and the explicit `date` fields on goal-log/eyerest/
mistake rows are already wall-clock-safe. What is not safe is arithmetic across a
move, and that is what this section is about.

### The two clocks

Instants are continuous and never repeat. Local dates are a *labelling* of them
that a move can tear: fly Bangkok→New York and the label `2026-08-20` gets stuck
on 33 hours of real time; fly the other way and it covers 22. So "what happened
on the 20th" is not answered by a 24-hour box — it is answered by asking which
stretches of the real timeline were wearing that date. `dateZoneSegments(date)`
in `app.js` is that question, and every honest number downstream falls out of it.

The invariant that holds is about a *run* of dates, not one date: total real
minutes across them = 1440 per date minus the offset change. The tempting
shortcut — "the travel day is 1440 minus the change" — is only true when the move
leaves the local date alone. `tests/timezone-transitions.test.js` pins this.

### The transition log

`timezone-history.json` holds one row per zone change: `{id, from, to, at,
atInstant, eventId, source, approximate, note}`. `at` is wall clock in the zone
being **left**; `atInstant` is derived from it on every normalisation and never
trusted from the payload, so correcting a time in Settings cannot leave the
arithmetic pointing at the old moment. A row is a moment, not a date, because a
date cannot say which of a travel day's two mornings came first.

Rows are normally written by the calendar: tick the globe on the flight, and the
block owns the row (`eventId`). Editing the flight moves the transition, deleting
it removes the transition, and `reconcileZoneTransitionsWithCalendar()` clears
orphans on load. Settings → Time zones is for the two cases a block cannot cover:
a move with no block, and fixing a clock that was a guess.

The device zone is **evidence, not testimony**. A machine that was shut for the
flight, a VPN, or a hand-set zone can all say the wrong thing, and a wrong row
bends a year of totals. So a mismatch becomes the `suggestion` field on
`GET /api/timezone-history` and a question in Settings. Do not make it write.

### Three fields on an event

- `zone` — what clock the stored `start`/`end` are written in. Provenance.
- `tz` — what the event is **pegged** to; empty is the floating default. A pegged
  event is a fixed instant wearing a local face (the 09:00 Taipei standup) and
  slides when you move. A floating one is a wall-clock promise (the 07:00 run)
  and must never move. Synced Google/Outlook events are pegged; all-day rows
  stay floating, since a date has no instant.
- `zoneShift` — `{from, to, when}` on the rare block that *is* a move.

`normalizeCalendarEvent()` in `app.js` re-localises pegged events into the zone
returned by `calendarViewZone()`; `server.cjs` **preserves these fields and never
converts**, because one server can feed a laptop in one zone and a phone that
is still on another, and whichever asked last would win.

Both **stored** endpoints of an event always live in one zone, which is quietly
why a flight comes out the right length: 09:00 Taipei to 13:40 Taipei is four
hours forty, the same four hours forty a Bangkok clock calls 12:40.

But that is a storage fact, not what the person types. A `zoneShift` block reads
**like its ticket**: Start is the departure zone's clock, End is the
destination's. The editor shows it that way (`calendarEditorZoneView()`), the
grid block labels it that way (`calendarEventTimeLabel()`), and on save
`zoneShiftEndFromTicket()` is the one place a ticket end is rewritten into the
start's zone. When only clocks were typed, the end's *date* is settled by
instant — the first moment at or after departure wearing that clock — because
comparing clocks across two zones is exactly what the date line inverts (Tokyo
17:00 → Los Angeles 10:00 reads backwards on paper and is a nine-hour flight on
the same LA date). An explicit end date is read as the destination's date.

The editor shows a pegged event **in its peg zone** (`calendarEditorZoneView()`).
Showing the Taipei 09:00 as the Bangkok 08:00 it is stored as would make the next
save read that 08:00 back as a Taipei 08:00 and walk the meeting an hour earlier
every time it was opened.

### The transit log

The answer to "where do I write what I did on the plane". A `zoneShift` block
gets one prominent button in the editor (`transitLogControls()`); behind it, one
text row per **real elapsed hour** of the block, each labelled with both wall
clocks at the top of the hour. Elapsed hours are zone-free — hour 7 of the
journey is hour 7 whatever any clock says — so nothing in this panel ever needs
converting, and the journal's divider machinery is irrelevant to it. Stored on
the event as `transitLog` (array of strings, index = hours since the start
instant, capped at 48, trailing blanks trimmed); `server.cjs` mirrors the
normalisation (`normalizeTransitLog`) and, as with every zone field, preserves
without interpreting. Rows rebuild when the times or zones in the form change,
but never while typing inside a row (the input handler skips `transitHour`
targets, or focus would be pulled from under the cursor).

One block per move also holds for plan/actual pairs:
`eventOwnsZoneTransition()` makes an actual block outrank a plan block carrying
the same move within 48h, so "I did it" on a flight does not leave two
transition rows — and two journal dividers — fifteen minutes apart.

### Picking a zone

`zoneSelect()` builds every zone dropdown in the app. It returns a **wrapper
div**, not a `<select>` — a search box, the select, and a star — with a `value`
getter/setter forwarded to the select so callers read it unchanged. The select
keeps the `name`, so `FormData` reads it exactly as it read a plain dropdown and
nothing downstream had to learn about any of this. The search box is deliberately
unnamed, and swallows Enter so searching inside the event editor cannot submit
the form.

Order is **by GMT offset, west to east** — one optgroup per offset, cities
alphabetical inside it — because that is the axis a person thinks along. IANA's
own alphabetical order puts Adak next to Anchorage next to Anguilla, which tells
you nothing. Offsets are read at today's instant, so a zone on summer time sorts
where its clock currently sits.

Above the offset groups sits **My time zones**: `favoriteTimeZones` (starred, in
the user's own order, persisted in `app-settings.json`) followed by the zones the
data proves are in use — the machine's, the log's, anything an event is pegged
to. Starring is available wherever a zone is picked; unstarring is in Settings →
Time zones, which also shows the derived ones as unstarred chips that can be
pinned. Search matches city, IANA name and offset text, all words required, so
`asia 9` and `gmt+07` both work. A value filtered out from under the selection is
re-added as a "(not in this search)" option rather than being silently blanked.

### The view zone

`calendarViewZoneMode` is `"lived"` (default), `"device"`, or an IANA name, and
the picker sits where the static GMT label used to be. `"lived"` draws every day
in the zone that was on the wall that day, and costs nothing to render because
the stored clocks are already the lived ones. Changing the mode re-normalises the
whole in-memory calendar, so the day index, the grids and the totals keep working
in one consistent clock and none of them has to know the view zone exists.

### Travel days on screen

- **Journal divider.** `ensureZoneDividersForDate()` writes
  `— time zone changed: Taipei → Bangkok, 13:20 becomes 12:20 —` into the day's
  document. `extractHours()` treats it as a segment break and returns
  `{plain, categories, segments}`. Without it the crossed-noon heuristic (the
  `lastMinute` +720 rule, which fires on a backwards jump of more than two hours)
  files the morning after a long-haul landing as the evening — silently. The
  merged `plain`/`categories` stay exactly what every existing caller expects.
- **Hour grid.** Still 24 editable rows bound to one entry file per date. That is
  deliberate: forking the entry schema for a twice-a-year event would change the
  survey export, the search index and every date-keyed structure in the app.
  What the rows get instead is the truth written on them — a banner with the day's
  real length, `×2` on hours lived twice, dimming on hours that never happened.
- **Calendar column.** A labelled rule where the clock jumped, a hatched band over
  a skipped stretch, a tinted band over a repeated one, and a ✈ on the day header.
  Blocks are still placed by clock; the existing overlap laning stacks the two
  12:30s.
- **Durations.** `realMinutesBetweenClocks()` (next to `workSessionRow()`, inside
  the chunk `work-week.test.js` extracts, with a `typeof` guard so the harness
  still loads) places both clocks on the day's segments. Work 08:00–17:00 across
  an hour going back and the clocks say nine hours; you were at it for ten, and
  every hours total in the app would inherit the wrong nine.
- **Goals and streaks.** `isShortZoneDate()` — under six hours lived, or a date
  the date line ate — books no miss in `expireDailyGoalTasks()` and is skipped by
  `trendsGoalStreaks()`. Getting on a plane is not a missed habit, and it is not
  adherence either.

### Known limits

- A recurring **pegged** event uses its base date's offset for every occurrence,
  so a series spanning a DST change is an hour out on the far side. Recurring
  floating events — nearly all of them — are unaffected.
- A date lived twice keeps **one** entry file and one set of surveys. The hour
  grid's segments carry both passes; the day total may exceed 24 hours.

## Calendar Behavior

The calendar is native to the app. It persists to `calendar-events.json` and syncs with Google Calendar in both directions: Google events come in read-only, and local plan blocks go out.

Google Calendar sync is two-way. The server stores OAuth credentials/tokens locally and uses the `https://www.googleapis.com/auth/calendar.events` scope (read **and** write; it was `.events.readonly` until 2026-09-10, which is why the push never worked -- a connection made under the old scope stays one-way until the account is reconnected, and `googleScopeAllowsWrite()` gates the push on the granted scope, not the requested one).

**Pull.** Imports from the configured calendar ID (default `primary`) and tags imported events with `source: "google"`, `calendarId`, and `providerId`. Sync preserves local category and plan/actual classification for matching imported events, but title/time/location/link/description continue to come from Google. Imported Google events should not be dragged/resized locally; copying a plan to actual creates a separate local actual event.

**Push.** Live local plan blocks (`kind: "plan"`, `source: "local"`, no `supersededAt`) are written up to the same calendar. Actuals, deadlines, archived old plans and imported events are never pushed, and a block that stops qualifying is *deleted* from Google rather than merely skipped. Rules that must hold:

- The push runs **before** the pull in `syncGoogleCalendar()`, and the pull drops any imported event whose `providerId` is in `push.pushedIds`. Reverse the order and the sync imports its own freshly-created blocks back as read-only twins.
- `auth.pushSince` is stamped on the first sync that has write scope, and only blocks written at or after it are newly eligible. This is what makes turning the push on not a bulk backfill of the whole file. It survives reconnects on purpose.
- `google-calendar-push.json` is the ledger: `localId -> { googleEventId, updatedAt, calendarId }`. It is what lets a *deleted* local block still be withdrawn from Google, so it cannot be replaced by a field on the event alone. It is removed on disconnect.
- `googleEventId` is a normalizer field and must be kept by **both** normalizers, same as `supersededAt`/`taskId`/`deadlineId`. Any factory that spreads an existing event under a new local id (blank event, detach-occurrence, split, plan-to-actual) must clear it, or two blocks claim one Google event.
- `repeatDays` is `getDay()` order (0 = Sunday) and maps to `BYDAY` through a Sunday-first table. All-day pushes use Google's exclusive end date.

`tests/google-push.test.js` covers the mapping and the normalizer fields; `tests/google-push-run.test.js` runs whole syncs against a fake Google and covers the create/update/delete passes and the ledger.

A dead refresh token comes back from Google as `invalid_grant` with `error_description: "Bad Request"`. `requestGoogleToken()` rewrites that into a message naming the cause, because the raw text is why a sync that had been failing since 2026-08-16 read as an ordinary hiccup for a month. The usual cause is an OAuth consent screen left in **Testing**, where Google expires refresh tokens after 7 days.

Current behavior to preserve:

- 24-hour day/week grids, 12 AM through 12 AM.
- Week view is a unified Google-calendar-like grid.
- Red current-time bar.
- Click/drag to create events with 5-minute snapping.
- Drag event body to move it.
- Drag event top or bottom edge to resize it.
- Week-view event dragging and resizing can cross day columns.
- A drag moves the block, not the calendar. `updateCalendarEventMove()` and `updateCalendarEventResize()` write `top`/`height` (and the day column, by re-parenting) on the one dragged block through `paintCalendarBlockRange()`, and rewrite the clock in its time row; the event record is not touched until the pointer is released. Both used to write the new times onto the event and call `renderCalendarView()` on every `pointermove`, which rebuilt the whole view -- measured at ~165ms on an ordinary week (55ms of it building 120 blocks, 44ms in the text fit), so a drag ran at about six frames a second. Per-move cost is now ~3ms. Do not put a full render back on a pointer path.
- The consequence, and it is deliberate: overlap lanes do not reflow under the pointer. The dragged block gets `.is-dragging` (an inline `z-index`, because `calendarEventBlock()` writes one there from the layout depth and inline beats a class rule) and floats over its neighbours until it lands; the drop's render settles the lanes.
- Every way a drag ends re-renders, which is also what clears the preview: `finishCalendarEventMove()`, `cancelCalendarEventMove()`, and the same pair for resize. Because nothing was written to the record, a cancel needs no undo and the recurring scope prompt still finds the series holding its original times.
- Multi-day timed events are stored as one event and rendered as clipped per-day segments.
- Overlapping/conflicting events stack visibly, as a cascade
  (`layoutCalendarEventCascade()`): every block keeps its full width and the
  **shorter block is always drawn on top**, stepped `CALENDAR_OVERLAP_STEP_PX`
  right of the one under it, so what shows of the block underneath for the
  shared hours is a leak of its left edge. Equal lengths: the later one is on
  top. It used to be "later on top", which put a 9:05-12:00 work block over a
  9:00-9:30 call and left the call a 5-minute head and a 14px leak -- the
  "smaller event disappears inside a bigger one" bug (fixed 2026-09-08). The
  price is paid by the long block instead: `calendarHeadCoverMinutes()` works
  out how far into it the shorter blocks over its head reach (chained, with
  `CALENDAR_HEAD_COVER_SLACK_MINUTES` of tolerance between one cover and the
  next) and `calendarEventBlock()` turns that into `--head-cover`, extra
  `padding-top` in hour-height units, so the long block's text starts below
  the covers. Padding rather than a spacer because the text fit already
  subtracts padding. `tests/calendar-cascade.test.js` pins the rule.
- In `both` filter, plan events are left-aligned, actual events are right-aligned, and the center remains open for adding new events.
- Plan event editor has an `I did it`/copy-to-actual flow that creates an actual event at the same time.
- Recurring events have separate delete paths for occurrence vs series.
- Calendar-only zoom, independent of browser/app zoom (see below).

The footer strip:

- `.mini-row` under the work area is the single footer for every view: whatever the open view wants to say on the left (`#miniRowStatus`), the actions on the right. `renderMiniRow()` fills it, and is called from both `render()` and `renderCalendarView()`.

Calendar zoom:

- Zoom stretches the hour rows and nothing else. Text size, the toolbar, the day-header row, the time-zone label and the column widths are the same at every zoom level -- that is the requested behavior, not an oversight. Do not reintroduce font or whole-grid scaling (an earlier CSS `zoom` version did exactly that and was rejected).
- The toolbar has a `− / 100% / +` control; the percentage button resets to 100%. `Ctrl + scroll` (or trackpad pinch) over the time grid zooms and is `preventDefault`ed so the browser does not zoom the whole app instead.
- Levels are the fixed `CALENDAR_ZOOM_LEVELS` steps (70%-350%). `calendarZoom` persists in `app-settings.json`, is snapped to a level by `normalizeCalendarZoom()` on load, and is deliberately left out of `appHistorySnapshot()` so undo never changes zoom.
- Implementation is one CSS custom property: `applyCalendarZoom()` sets `--calendar-zoom` on the calendar view. `.calendar-view` derives `--calendar-hour-height` (`calc(54px * var(--calendar-zoom, 1))`) from it once, and that is what the `.calendar-time-axis` row height, the `.calendar-slot` min-height and a block's pushed-down text (`--head-cover`, see the cascade note above) read. State the hour height nowhere else; the axis and the slots must stay the same height or the hour labels drift off their lines.
- Everything else in the grid is positioned as a percentage of the day column (event blocks, draft preview, now line) and all pointer math comes from `getBoundingClientRect()`, so drag/create/resize need no zoom factor and stay exact.
- Month view has no hour rows, so it does not zoom and `calendarToolbar()` omits the control there.
- `setCalendarZoom()` takes an optional `anchorClientY` so scroll-zooming keeps the hour under the pointer in place instead of jumping; it measures from `.calendar-grid-days` because the day headers above it do not stretch. It does not re-render -- it only updates the property, the label and the text fit.

Event blocks and text fitting:

- A block's height is its duration, so text is cut to the box rather than the box grown to the text. `.calendar-event-chip` sets `overflow: hidden` and clamps its title to `--title-lines`. Do not remove either: before them a long title painted straight out of its block and across its neighbours, which is what made a busy week look like overlapping garbage.
- CSS, not JS, is what keeps the title off the time row: `.calendar-event-chip.calendar-event-block strong` is capped with `max-height: 100%`, which resolves against its 1fr grid area. This holds even at the unclamped `--title-lines` default, so a fit that has not run yet, or ran at a different height, costs a line of title rather than a title painted over the time. Do not drop that cap on the assumption that the fit is always current -- it was not, and the titles came out looking struck through.
- `fitCalendarEventBlocks(blocks)` sets `--title-lines` per block from the height it actually got, in a three-step ladder: `is-tiny` (under 34px -- one line, no time row, padding down to 1px), `is-compact` (title only, full height), or the full layout with the title clamped to the lines left above the time row. It resets every block in the batch before measuring any of them, so a re-fit never reads a box that is mid-decision. `fitCalendarEventText()` is the same thing over every block on the page.
- Blocks re-fit themselves: `observeCalendarEventBlock()` puts each one in a `ResizeObserver` (border-box, so `is-tiny`'s padding change is not read back as a resize), and `renderCalendarView()` calls `resetCalendarTextFitObserver()` before it wipes the view so the old targets are released. That covers zoom, window and pane resizes, and the first measurement -- delivered before paint, so no unfitted frame. Geometry changes do not need to remember to call the fit; the old code did, and the paths that forgot left stale line counts behind.
- The observer, like `requestAnimationFrame`, delivers nothing while the document is hidden or occluded -- which is why `renderCalendarView()` also fits synchronously, and why the CSS cap above exists.
- Line heights are measured off the elements (`measuredLineHeight()`), so `styles.css` is the only place the type is stated. `CALENDAR_FALLBACK_LINE_HEIGHT` (15) is only for a `line-height` that reads back as `normal`.
- The time row is pinned to one line (`white-space: nowrap` + ellipsis on the block's `span`). It must stay that way: in a narrow week column `9:05 AM-11:00 AM · actual` wraps to five lines and the fit, which budgets exactly one line for it, would hand the title more room than it has.
- Colour is said once, by the 4px bar on the leading edge. The fill is a 9% mix and the border 18%; `readableEventColors()` mixes the same 9% background to pick text colour, so the two must change together.

Long titles:

- `splitLongCalendarTitle()` in `normalizeCalendarEvent` cuts any title over `CALENDAR_TITLE_MAX_CHARS` (60) down to a headline and keeps the full text as the first paragraph of the event's notes. It breaks at a sentence/clause mark, else a word boundary, else blindly; a break inside the first 40% is ignored as too short to name anything.
- It is idempotent by construction: the cut is clamped to `MAX - 1` so the result plus its ellipsis comes back under the limit. Without that clamp a title with no break in it loses a character on every load. If you change the ellipsis or the limit, re-check that a 300-character unbroken title is stable across repeated normalisation.
- `calendarEventFullTitle(event)` is the way back to what was typed -- it returns the first paragraph of notes when the title ends in an ellipsis. Anything exporting off the calendar should use it.

Deadlines and FYI events (added 2026-08-24):

- An event's `kind` is now three-valued: `plan`, `actual`, `deadline`. Both
  normalisers (`normalizeCalendarEvent()` in `app.js` **and** `server.cjs`)
  know all three; an older copy of either flattens `deadline` back to `plan`,
  which is why the server must be restarted when this schema changes.
- A **deadline** is a moment, not a span: `start` is the due time and the
  normalisers pin `end` to it, so it can never grow into a block. It carries
  `estimateMinutes` (same 0 = "not estimated" rule as tasks) — how long the
  work is expected to take, which sizes the plan block placed from it.
  Recurrence works (weekly problem sets); an all-day deadline is due 23:59.
- On the grid a deadline draws as `calendar-deadline-line` — a 2px dotted rule
  in the now line's red (`CALENDAR_DEADLINE_COLOR`), clickable to edit, never
  draggable/resizable, excluded from the block layout. In month cells and the
  all-day row it is a hollow dotted-red chip. It ignores the plan/actual filter
  entirely: `calendarEventVisible()` always shows deadlines.
- **The nag**: an upcoming deadline with no booked work block appears in
  "Deadlines to plan" — a panel above the Tasks view sections and a group on
  the rail, both built from `upcomingDeadlineItems()` and `deadlineNagRow()`.
  Its `◷` runs the same click-to-arm placement as tasks
  (`startDeadlinePlacement()` → `armTaskPlacementMode()`); the dropped plan
  block carries `deadlineId` back to the deadline, which is what clears the
  row. Like `taskId`, `deadlineId` must exist in both normalisers or a save
  silently un-plans every deadline. "Booked" means a linked plan block from
  today onward (`deadlinePlanEvents()`) — a past block is history, so a missed
  work session re-surfaces the deadline. The deadline editor shows the booked
  block (or "No work time booked yet") with a "Plan work time" button.
- Deadlines stay out of the numbers: `trendsDayBlocks()` skips them (their
  zero length would read as a block running to midnight through the
  midnight-clip rule), coverage and work-hours filters never match them, and
  `planEventIndex()` only indexes `kind: "plan"`.
- A **tentative** (FYI) event is a plan block that is not a commitment —
  office hours, drop-ins. `tentative` is a boolean both normalisers keep only
  on `kind: "plan"`. Ghosted at 0.55 opacity with a dotted border
  (`is-tentative`), labelled `· fyi` in the time row, hidden entirely by the
  toolbar **FYI** toggle (`calendarShowTentative`, persisted in
  `app-settings.json`), and excluded from "Planned hours against logged hours"
  in Trends — office hours skipped are not hours missed. Deliberately still
  eligible for "I did it" and estimate pairing: attending office hours is real
  data.

Old plans / re-planning (added 2026-08-28):

- When reality breaks a day's plan, the plan is **archived, not deleted**. A
  plan event carries `supersededAt` — the ISO stamp of the moment it was
  archived; empty means it is the current plan. The field lives in **both**
  normalisers (`app.js` and `server.cjs`), plan-kind only, and like
  `taskId`/`deadlineId` dropping it from either side silently resurrects (or
  kills) every old plan on the next save round-trip. Server restart required
  when touching this, as with every calendar schema change.
- **Re-plan** is a toolbar button, day view only, hidden in the `actual`
  filter. `archiveCurrentDayPlan(date)` stamps one shared `supersededAt` onto
  every current, non-recurring, non-tentative, non-all-day, local plan block
  touching the day — restricted to blocks that have not ended yet when the day
  is today, so a morning that ran as planned stays in the main lane and the
  day's effective plan reads as old morning + new afternoon. Recurring blocks
  are standing commitments and stay put; FYI blocks were never commitments;
  imported blocks are not ours to archive.
- **One stamp = one old plan = one rail.** `calendarTimedEventLayouts()`
  groups superseded events by stamp into thin rails on the left edge of the
  day column (`CALENDAR_OLD_PLAN_RAIL_WIDTH` each, strip capped at 0.18),
  oldest leftmost, and starts the current plan to the right of the strip. The
  rail element (`calendarOldPlanRail()`, `.calendar-old-plan-rail`) is the
  click target; the blocks inside it render as `is-sliver` chips —
  `pointer-events: none`, text hidden, skipped by the text-fit observer, never
  draggable/resizable.
- Clicking a rail swaps that generation in over the current plan's range
  (`is-old-plan-open`, laid out at depth 6 so it stacks above) — dashed,
  lifted, clickable through to the editor; clicking the rail again puts it
  away. One open at a time, held in `calendarExpandedOldPlanStamp`, in-memory
  only. The editor on an archived block offers **Restore to current plan**
  (per-block — half the point of re-planning is that only some of the old plan
  was wrong); "I did it" stays, since doing what the old plan said is real
  data.
- Old plans are display-only history everywhere else: `planEventIndex()` skips
  them (the ◷ button must not light off a withdrawn plan),
  `deadlinePlanEvents()` skips them (archiving a booked work block re-surfaces
  the deadline nag — deliberately), `trendsDayBlocks()` skips them (a
  withdrawn plan was not missed; the current plan is the plan of record), and
  month cells filter them out. In day/week they still pass
  `calendarEventVisible()` — collapsing is a layout decision, not a
  visibility one, so the plan/both/actual filter semantics are untouched.
- `tests/plan-supersede.test.js` guards the two normalisers, the rail/sliver
  geometry, cross-generation containment, and the deadline-booking exclusion.

Work sessions (category `W`):

- Work mode books its closed sittings as category-less `Work session` blocks;
  see "Work Mode" above. The upstream app also hung hours reporting on category
  `W`, and none of that is in this fork. If you want
  hours out of here, `workSessionsInRange()` is gone but `calendarRangeDates()`,
  `realMinutesBetweenClocks()` and `formatWorkDuration()` are the pieces it was
  built from. `realMinutesBetweenClocks()` is the one that matters: it is what
  stops a travel day counting nine hours when ten were worked.

## HUD Behavior

The HUD is implemented in `task-hud.ps1` as a WPF window.

Current intended behavior:

- Floating topmost utility window.
- Hidden from Alt-Tab and normal taskbar.
- Minimize button hides the HUD.
- `launch-task-hud.ps1` restores an existing HUD window when possible instead of creating duplicates.
- Separate `Event Horizon HUD.lnk` launcher can be pinned to taskbar and uses `hud-check.ico`.
- Shows the whole `rightNow` stack (up to `maxVisibleTasks` rows, default 5, then a "+N more" line), one checkmark per task, so multiple in-flight tasks stay visible at once. The first row is the current task (bright green check, brighter text); later rows are dimmed.
- Rows are rebuilt only when the task list actually changes (id/text signature compare) so the 2s poll does not churn click targets.
- The `−` / `+` buttons in the HUD header change how many rows are listed (1-12) and persist as `maxVisibleTasks` in `hud-settings.json`. They rebuild from the cached task list, so the change is immediate rather than waiting for the 2s poll.
- Window height is auto-computed from the row count. `hud-settings.json` stores `rowHeight` (per-row height, not total window height; old `height` values are migrated); dragging the resize grip rescales rows/fonts rather than clipping.
- Completing any row calls `/api/tasks/complete` with that task's id (section `rightNow`).
- `Ctrl+Z` in HUD calls `/api/tasks/undo`.
- Checkmark click launches a full-screen celebration overlay from the clicked row's button. `Start-Celebration` picks randomly from `$script:celebrationKinds` (confetti, fire, letsgo, bowling, fireworks, coins) and never repeats the previous one back-to-back.
- The enabled set comes from `celebrations` in `app-settings.json`, re-read on every completion so Settings changes apply without restarting the HUD. A missing key counts as enabled; a missing or corrupt file falls back to all enabled. All off means no animation plays.
- Toggles live in the app's Settings view (`celebrationsPanel` in `app.js`); `CELEBRATION_KINDS` there must stay in sync with `$script:celebrationKinds` in the HUD.
- Celebration overlays must remain hidden from Alt-Tab/taskbar.
- Each celebration builds its own overlay window and owns its own close timer, so overlapping completions do not orphan an overlay on screen.
- Celebration art is all vector geometry. WPF and GDI both render color emoji as flat black glyphs, so emoji cannot be used for this.
- `BeginAnimation` replaces any prior animation on the same property; multi-stage motion (fade in then out, roll in then fly off) must use `New-CelebrationKeyAnim`, not two calls.
- Overlays span the virtual desktop; center staged pieces on `$Context.Screen` dimensions rather than assuming the primary monitor.

Celebration performance matters and is easy to wreck. A transparent full-screen window is a per-pixel-alpha layered window, so WPF renders it in **software**: every frame recomposes the whole screen on the CPU. Rules:

- No `DropShadowEffect`/blur on anything that repeats. Use a radial-gradient halo instead. The one exception is the single headline TextBlock, which is bitmap-cached.
- Get brushes from `New-CelebrationBrush`/`New-CelebrationGradient`/`New-CelebrationRadialBrush` and geometry from `Get-CelebrationGeometry`; they cache and freeze, so hundreds of particles share a handful of objects.
- Animations are capped to `$script:celebrationFrameRate`; the constructors apply it.
- Fade groups of particles by animating one parent layer's opacity, not one clock per particle.
- Put multi-part vector art (flames, pins, coins) behind `Set-CelebrationCache` so it rasterizes once.

Windows virtual desktops are awkward. A normal WPF script window does not have a robust official "show on all desktops" setting. Avoid brittle private virtual-desktop APIs unless the user explicitly chooses that tradeoff.

### HUD usage logging

Before this existed the HUD left no trace but its window position, so "does
having the HUD open change what I get done?" was unanswerable. Two things now
record it:

- `Write-HudLog` in `task-hud.ps1` posts to `POST /api/hud-log`, which appends a
  row to `hud-log.json` through `queueHudLogAppend` (same chained-promise
  read-modify-write as `queueGoalLogAppend`/`queueEyeRestLogAppend`). Kinds:
  `start`/`end` bracket a session, `show`/`hide` track tray visibility inside
  one, `complete`/`undo` mark task actions taken in the HUD. `GET /api/hud-log`
  takes the same `from`/`to` params as `/api/eyerest-log`.
- Every row carries `sessionId`, a GUID generated once per launch. A session is
  reconstructed by pairing `start` with the `end` holding the same id; a HUD that
  is killed rather than closed simply never writes its `end`, so consumers must
  treat a missing `end` as an open-ended session, not a zero-length one. `start`
  is written from `Add_Loaded` (after the duplicate-launch guard exits), `end`
  from `Add_Closed` with `durationSeconds`.
- Logging is best effort and never surfaces failure: a HUD that cannot reach the
  server is still a working HUD. This also means an offline stretch is missing
  from the log entirely rather than recorded as inactivity.

Which surface completed a task is tracked separately on the task itself:
`completedVia` is `"hud"` (set by `/api/tasks/complete`, which the HUD calls with
`via: "hud"`) or `"app"` (set by `completeTask()` in `app.js`). It is whitelisted
in both `normalizeTask` implementations against `TASK_COMPLETION_SURFACES` /
`taskCompletionSurfaces`, so adding a third surface means editing both. `null`
means the task was completed before the field existed -- any HUD-vs-app
comparison has to start from the first date the field appears, not from the start
of the task history.

## Work Mode (Ctrl+Alt+F)

`work-mode.ps1`, launched by `launch-work-mode.vbs`. A second kind of HUD with a
different job from `task-hud.ps1`: the HUD says what to do next, work mode says
you are supposed to be working at all. It never talks to the server, so it comes
up on a machine where nothing else in the app is running.

- Four opaque WPF windows, one per screen edge, painted electric green
  `#64FA87` (`#00CD3C` is the text green and reads as almost black at 7px).
  Every window is topmost, `WS_EX_TOOLWINDOW`, `WS_EX_NOACTIVATE` and
  `WS_EX_TRANSPARENT`, so the band is paint on the glass: it never takes focus
  and never swallows a click.
- Opaque, not transparent, on purpose. A full-screen per-pixel-alpha layered
  window forces WPF into software rendering (see the celebration notes above);
  four thin solid rectangles stay hardware-composited.
- **Never add `WS_EX_LAYERED` to the band windows.** A window that is not already
  layered goes invisible the moment that bit is set unless
  `SetLayeredWindowAttributes` follows. `WS_EX_TRANSPARENT` alone is what makes
  the mouse pass through. The pill is a separate case: `AllowsTransparency`
  makes WPF set the layered bit itself.
- Placement goes through `SetWindowPos` in physical pixels
  (`WorkModeNative::PlaceAt`), not WPF's `Left`/`Top`/`Width`/`Height`, which are
  device-independent units. `Screen.Bounds` is in the same physical space, so
  this sidesteps DPI scaling instead of converting between the two. WPF still
  re-imposes its own idea of the rectangle on `Show()`, which is why
  `Set-BandRect` stores each rect and re-applies it after every un-hide.
- Three band moods, kept separate so the band never says two things at once:
  green steady (working), dim `#33453B` steady (an eye-rest break is running),
  red pulsing (a distracting window is in front of you). Overrunning the pomodoro
  is deliberately *not* a band mood - it shows in the pill, because being over
  time and being distracted are different problems.
- Settings live in `work-mode-settings.json`, read once at launch and written on
  every tray change. Out-of-range values are clamped rather than rejected.
- `workModeOn` is saved (every tray change saves the whole object) but is
  **forced back to true at launch**. It describes a state during a session, not a
  preference for the next one: you start work mode because you want to work, and
  a launch that quietly comes up hidden is indistinguishable from one that
  failed. Do not "fix" this by honouring the saved value.
- Auto-starts from `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\Journal Work Mode.lnk`
  (`wscript.exe "…\launch-work-mode.vbs"`, `hud-check.ico`), the same pattern as
  the five capture listeners. Startup takes 30-90s of `Add-Type` compilation
  before the band paints, so "nothing happened" right after a launch means
  nothing yet.

### Pomodoro

- A 30-minute default, shown in a click-through rounded pill anchored to the
  bottom of the **working area** (not the full bounds), so it does not sit on top
  of the taskbar's pinned icons. `pillPosition` accepts
  `top`/`bottom` optionally suffixed `-left`/`-right`.
- Held as an end timestamp, not a decrementing counter, so a missed tick cannot
  make it drift and a machine that sleeps wakes up correctly deep in the
  negatives rather than where it left off.
- It does not stop at zero. Remaining seconds go negative and the pill switches
  to `OVER +MM:SS` in amber, because overrunning is information.
  `chimeAtZero` plays one system sound on the crossing.

### Eye-rest handshake

`eyerest-capture.ps1` writes `eyerest-state.json` (`state` = `idle`/`running`/
`review`, `outcome` = `""`/`logged`/`discarded`, `changedAt`) on every stage
change, and work mode polls it, re-parsing only when the file's mtime moves.

- A file rather than an API call, for the same reason the outbox exists: a
  capture must never depend on the server being up, and work mode must not be
  what reintroduces that dependency. It is also the only honest signal, because
  Esc hides the eye-rest window while the session keeps running, so "is the
  window on screen" answers a different question.
- `running`/`review` pauses the pomodoro and dims the band; back to `idle`
  resumes it. `outcome: logged` also resets it to a fresh 30 minutes
  (`resetAfterEyeRest`); `discarded` only resumes. A discarded break still
  resumes, because leaving the timer paused forever would be a trap.
- A `running` state older than three hours is treated as `idle`, so a listener
  killed mid-session cannot pin the timer paused. The listener also writes
  `idle` at launch for the same reason.
- Editing `eyerest-capture.ps1` means restarting that listener before any of
  this takes effect (see the note at the top of `AGENTS.md`).

### Work sessions on the calendar

Switching work mode off books the sitting as a hot-pink `Work session` block via
`POST /api/work-session` (`addWorkSession` in `server.cjs`).

- The event is **uncategorised on purpose**. `app.js` resolves a colour as
  `categoryColor(category) || event.color`, so any category would win and the
  pink would never render. The pink is the point: the block is a to-do, not a
  record, and it stays the one colour on the calendar meaning "not filed yet"
  until you categorise it by hand.
- `#ff1493`, not CSS hot pink `#ff69b4`, which is close enough to the Dating
  category's `#f472b6` to be mistaken for it at a glance.
- Minimum is five minutes of **working** time - elapsed minus any eye rest - so
  turning work mode on and immediately taking a long break books nothing.
  `WORK_SESSION_MIN_SECONDS` (server) and `$script:workSessionMinSeconds`
  (work-mode.ps1) are the same number in two places; the client check stops the
  usual case posting at all, the server one is the backstop for a replay.
- A session containing an eye rest gets `Includes N min of eye rest.` in its
  notes. Eye rest books its own H event across the same minutes, so the two
  overlap on the calendar, and the note is what stops the block reading as solid
  work at categorisation time. Note that the calendar's overlap rendering insets
  the containing block and gives the contained one a higher z-index, so a work
  session that fully contains another event shows only a pink edge.
- This is the one thing work mode sends anywhere. It goes through
  `Invoke-CapturePost` (`capture-outbox.ps1`), so a closed session parks in
  `outbox/` when the server is down and drains on its next start;
  `/api/work-session` is in `captureOutboxEndpoints` for that reason, and is
  idempotent on `captureId` like the four capture endpoints. A session too short
  to book answers `{ ok: true, skipped: true }` rather than a 400, or a replayed
  one would land in `outbox/rejected` as if it were bad data.
- The POST happens *after* the band is hidden, because an unreachable server
  costs it up to three seconds on the UI thread.
- The tray's `Exit work mode` closes the session too: quitting is turning it off.
  A rejection or an unwritable outbox raises a tray balloon, because a silently
  dropped session is exactly the thing this feature exists to prevent.

**Durability.** The open session used to live in memory alone, and a process
killed rather than exited simply lost it - the old reasoning being that
resurrecting a partial session would book work that may have stopped hours
earlier. That was right about the risk and wrong about the fix. Work mode
launches with the band already on, so the ordinary end of a sitting is a
shutdown, a sleep or a logoff, and every one of those kills the process long
before `Stop-WorkSession` runs; two blocks reached the calendar in the first
eight days of use.

- The open session is now mirrored to `work-session-state.json` -
  `startedAt`, `heartbeatAt`, `restSeconds`, `captureId`, `ownerPid` - with the
  heartbeat rewritten every `$script:sessionHeartbeatSeconds` (10s) from the
  tick. Written to `.tmp` and renamed, so a half-written file is never visible.
- `Restore-WorkSession` runs once at launch, before the fresh session opens, and
  books a leftover file as `startedAt -> heartbeatAt`. The recovered block ends
  where the band was **last known to be up**, not whenever the machine came
  back, which is the measurement the old comment wanted and could not get. It
  costs up to one heartbeat interval off the end.
- The `captureId` is pinned when the session *starts*, not at post time, so a
  live post and a recovery of the same sitting carry the same id and the
  server's idempotency collapses them. The state file is cleared *before* the
  post for the same reason.
- Sleep is handled separately, because a heartbeat cannot tell a sleeping
  machine from a dead one. The tick runs once a second, so a gap over
  `$script:sessionGapSeconds` (90s) is the machine having been suspended or
  hung: `Update-WorkSessionContinuity` closes the sitting at the **last tick**
  and opens a new one on wake, instead of booking a night of sleep as ten hours
  of work.
- `Toggle-WorkMode` stamps the end instant before it touches the screen and
  wraps the band/pill/tray/settings work in a `try`, so a throw on screen can no
  longer swallow the session behind it.
- Every decision is appended to `work-mode-log.json` (last 500 rows):
  `session-start`, `session-posted`, `session-skipped-short`, `session-dropped`,
  `session-recovered`, `session-split-on-gap`, `toggle-ui-error`. A session
  dropped for being under the five-minute floor used to look exactly like a
  hotkey that never fired; **that is the file to read first** when a block is
  missing from the calendar.

### Distraction watch

- Every two seconds, the **foreground** window's title is matched
  case-insensitively against `distractionPatterns`, gated on the foreground
  process name being in `distractionProcesses` (empty list = any process). Two
  consecutive hits turn the band red; one miss clears it immediately.
- Foreground only, not every window: a distracting page parked in a background
  tab is not what breaks a work session, and a minimised window would otherwise
  pin the band red all day. The cost is that a background tab is invisible to it.
- Titles are all it has, so a site whose `<title>` never names itself cannot be
  caught. chess.com is the awkward one - its pages are titled things like
  "Play Chess Online - Free Games" - so both spellings ship in the defaults.
  The list is data in `work-mode-settings.json`, not compiled in.
- Keep `distractionProcesses` populated unless you want false positives: without
  it, a Word document named "youtube plan.docx" turns the band red.

### Hotkey

Ctrl+Alt+F (F for focus). **Not** Ctrl+Alt+W - that is `mistake-capture.ps1`.
Every capture listener owns a primary and a fallback list (E/R/Y, W, Q/J/U,
L/B/N, C/G/K); check them all before changing this. Falling back to
Ctrl+Shift+Alt+F or Ctrl+Alt+O is silent, because the tray icon is a complete
substitute and a message box over a missing convenience is not worth it.

Verifying a restart has the same trap as the capture listeners: the instance
mutex (`Local\JournalWorkMode`) is invisible from a sandboxed shell. The reliable
check is that `RegisterHotKey` for Ctrl+Alt+F fails - taken means alive.

## Trends View

Opened by the bar-chart icon button in the topbar (`#trendsViewButton`, next to
the Settings gear). It is a read-only analytics dashboard over the morning and
night survey history: stat tiles (avg sleep, sleep quality, joy, weight, survey
completion), SVG line charts (sleep duration, sleep ratings, mood/accomplishment,
weight), and frequency bar charts for the multi/single-choice questions
(disruptions, intention check, people, exercise, hobbies), with a
30/90/365/all date-range filter row that scopes every card.

Implementation notes:

- All code sits in one marked section at the end of `app.js` (`renderTrendsView`
  and `trends*`/`buildTrends*` helpers) and one section at the end of
  `styles.css`. It reads only `state.entries` (already loaded by
  `/api/entries`) — no server calls, no writes. `activeView === "trends"`.
- Survey answers are stored as the display strings the survey form writes, so
  the parsers mirror those formats: slider/form questions are composite
  `"Label: value; Label: value"` strings (split on `;`, then first `:` — times
  like `01:15` keep their colon because the label carries the first colon);
  multi-choice answers are `", "`-joined tokens. If the survey form ever changes
  its serialization, update `parseTrendsFields` / `multiCounts` to match.
- Sleep duration = "Time I woke up" − "Time I fell asleep" (+24h when it crosses
  midnight, discarded if > 20h). Weight accepts 60–500 only ("Didn't measure"
  parses to null and is skipped).
- Chart series colors are the `--chart-1..4` CSS variables (light set in
  `:root`, re-stepped dark set under `body[data-session="night"]`). This 4-slot
  palette was validated for colorblind separation and contrast against both
  panel surfaces — don't swap in arbitrary hues or reorder the slots without
  re-validating; every bar/end-point is also value-labeled and each line chart
  has a Data (table) toggle, which is the required relief for the two
  light-mode slots that sit below 3:1 contrast.
- Text (labels, values, legends) always uses `--ink`/`--muted`, never a series
  color; identity comes from the colored mark next to the text.
- Future-dated entries are excluded (`date <= todayISO()`), as are days where
  neither survey has any answer.
- Five "process" cards at the end of the grid are the exception to "reads only
  `state.entries`": they read `state.calendarEvents`, the module-level `goalLog`
  / `goalsDoc`, and entry `_revision`. They are still read-only. `trendsRangeBounds()`
  re-derives the same window `collectTrendsRows()` uses, as dates, so the range
  buttons scope them too.
  - *How far ahead plans were made* / *How soon hours were logged* bucket the gap
    between a calendar block's `createdAt` and its `start`/`end`. Buckets, not an
    average: the question is how often there was a plan at all, and a mean hides
    the retroactive blocks entirely.
  - **Timezone caveat.** Calendar `start`/`end` are local wall-clock strings with
    no zone; `createdAt` is a UTC instant. Subtracting them is correct only when
    the viewing timezone matches the one the block was created in. Historical
    lead times will shift if these are read from a different timezone than they
    were logged in — relevant to anyone whose entry data spans a move.
  - *Goal follow-through* is `checks / (checks + misses)`; *Goal coverage* is
    `answers / materialised`. Both sort weakest-first, which is the actionable
    order. Keep them separate cards — see "Derived Logging" for why.
  - `buildTrendsBarCard` takes optional `footNote` (cards not counting "answered
    days" supply their own wording) and `valueSuffix` (for the two percentage
    cards, whose denominators are per-row and so cannot use `percent`).
- `tests/trends-process.test.js` extracts these helpers and runs them over
  fabricated data. Its fixtures derive `createdAt` from the local wall-clock
  `start` rather than hard-coding both, so the buckets do not silently encode the
  author's UTC offset.

### Trends, second wave

A later block of cards in the same view, in its own marked section of `app.js`
("Trends, second wave") with its own CSS block. Same rules as above: read-only,
no server calls, scoped by the same range buttons. What is new is the source —
these read records the app was already keeping and never showed.

- **Estimate accuracy** / **Time multiplier by category**. A plan block is an
  estimate made visible; the actual block that follows is what happened.
  `trendsEstimatePairs()` matches them by `taskId` first and otherwise by same
  day plus identical title, because click-to-place only landed in August and
  almost the whole history predates it. **Each logged block is claimed at most
  once**, so a plan repeated three times in a day lines up with three separate
  actuals instead of all three scoring against the first. Median, never mean:
  one block that ran eight times over would wreck an average.
  - Known skew: `copyCalendarPlanToActual()` ("I did it") copies the plan's own
    times, so an unedited pair reads exactly 100%. Roughly half the matched
    pairs sit in the close-to-plan bucket for that reason. The signal is in the
    tails, which is why the bucket card exists alongside the multiplier.
- **Planned hours against logged hours** buckets `trendsDayBlocks()` by category
  and kind. A category with logged time and no plan says so in words rather than
  showing a misleading overrun.
- **What moves with what** is Pearson r over `trendsVariableTable()`, curated
  inputs against curated outcomes at lag 0 and lag 1, minimum n of 10. It is not
  an all-pairs sweep on purpose: at that count a handful clear r = 0.5 on noise
  alone. **Missing and zero are kept apart** — a day with no actual blocks has no
  `workHours` key rather than a zero, or the table would manufacture a
  correlation between not logging and everything else.
- **Habit grid** reads `goalLog` as a calendar rather than a rate: one outcome
  per (goal, date), newest wins, same reader contract as `trendsGoalTallies()`.
  A day the goal was never asked on is blank and the streak walk steps straight
  over it — context-scheduled goals are not asked outside their context, and a
  run of those days must neither break a streak nor pad one. Today's
  materialised-but-unanswered row is `pending` and is skipped the same way, so a
  streak does not break at breakfast.
- **Hour strips** split each block across every hour it spans, so a 90-minute
  session is not filed entirely under the hour it began in.
- **Journal volume** counts words in `entry.journal`, the plain-text mirror.

`trendsRangeDateList()` gives these cards a concrete date list, since "All time"
hands back an empty `from`. The `TRENDS_MAX_RANGE_DAYS` cap trims the *oldest*
end so the window always still reaches today.

### Night survey evidence panel

`appendNightEvidencePanel()` sits above the first night question and offers
answers read off the day's calendar blocks and completed tasks — exercise and
hobbies in the default survey; `NIGHT_EVIDENCE_RULES` is where more go.

**It does not auto-apply, and that is the difference from the sleep prefill
above.** Sleep detection is arithmetic on blocks whose whole purpose is
recording sleep. These are keyword guesses about what a block title meant, and
the same answers now feed the correlation and frequency cards — a manufactured
"exercised" would quietly become a finding. Suggest, let the click confirm.

Rules live in `NIGHT_EVIDENCE_RULES` (first matcher wins per block, so specific
patterns lead and `fallback` only catches what none of them recognised) and
`NIGHT_EVIDENCE_TASK_QUESTIONS` (matched on the whole choice text, so
"Brush teeth (morning)" needs a task saying exactly that). Values are filtered
against the question's live choice list, so a choice removed from the survey is
never silently reintroduced.

### Mistake pattern tags

`mistake.tags` is a free-form array with a starting vocabulary in
`MISTAKE_TAGS`; any tag typed on a row joins the picker for every later row.

Tags are deliberately **not** a `MISTAKE_COLUMNS` entry. Columns are what
`mistakeIsComplete()` requires, and a row must never read as unfinished for
lacking a tag. They appear only on the card in the Mistakes view, never in the
Ctrl+Alt+W window — naming the pattern is reflection, and asking for it
mid-mistake is what killed this log last time. `server.cjs`'s capture endpoint
writes `tags: []` and nothing else.

The TSV and markdown exports carry `Pattern` as a trailing column so the sheet
keeps its five-column prose shape. The All-days review leads with a tag
frequency row that doubles as a filter.

### Unlogged and unplanned hours

Two chips at the end of the `.mini-row` footer, built by `buildCoverageChips()`
off `coverageSummary()`. They exist to be driven to zero, so they read `Unlogged
clear` at zero rather than a row of `0h`.

An hour is **logged** when an `actual` block covers ≥ `HOUR_COVERAGE_THRESHOLD`
(60%) of it and **planned** when a `plan` block does. Category is irrelevant —
sleep counts as logged like anything else, the question being whether the hour is
accounted for, not whether it was productive. `allDay` blocks are skipped: one of
them would otherwise mark a whole day covered without saying anything.

`coverageSummary(dateString)` answers for the day and week **being looked at**,
not for today — `calendarFocusDate()` supplies the cursor, the same date the pace
bar uses. Paging back a week and being told about this one makes the footer
unreadable, half describing what is on screen and half not, and it matters more
here than on the bar: these counters are a to-do list, and one for a week you are
not looking at is not actionable.

"Up to now" survives that as a clamp rather than an assumption. A past week has
fully elapsed and is judged whole; the week containing now stops at this minute;
a week that has not started returns `elapsed: false` and the chips hide rather
than reporting a clean sheet nobody has earned. A cursor on a future day inside
the running week gets `dayElapsed: false` and the chip drops its day half, since
`0h Wed 19` there would read as an achievement.

The labels follow the window: `1h today · 1h since Sun` while the week is still
filling, `19h Wed 29 · 48h Jul 26 - Aug 1` once it is done.

Three rules that are easy to get wrong and are pinned by `tests/hour-coverage`:

- **The window stops at the current minute.** Hours that have not happened are
  not hours you failed to log.
- **The hour in progress is judged on elapsed minutes**, not on a full sixty, or
  a fully-logged half hour would report as a gap.
- **Spans are merged, not summed** (`mergeCoverageSpans()`). Two blocks over one
  hour cover it once; summing would let a double-booked morning pay for an empty
  afternoon.

`startOfCoverageWeek()` is **Sunday**-based, matching the grid's `startOfWeek()`.
The chips still say `since Sun` rather than `this week`, spelled from the week
they measure: an unlabelled number beside a differently-bounded one is exactly
the bug this footer used to have.

Everything in this footer takes its date from `calendarFocusDate()`. Anything
added here should do the same;
a footer where some parts follow the cursor and others follow the clock cannot be
read as a whole.

`refreshCoverageChips()` swaps them in place on the same minute tick that moves
the now line (`startCalendarNowLineUpdates()`) and on `visibilitychange`. It
replaces only the `.coverage-split` element rather than calling `renderMiniRow()`,
which would rebuild the whole footer under whoever was reading it.

### Quick-add parsing

`parseTaskInput()` also reads a length (`90m`, `1h30`, `2 hours`), a start time
(`2pm`, `14:30`, `at 3`) and a calendar category (`/W`, `/work`). It returns a
`tokens` array of every recognition, keyed by kind and position, and
`options.disabled` turns any of them back into plain words.

That split is what makes the chips under the field a control rather than a
readout: the parser stays the only thing that decides what a word means, and the
UI just tells it which decisions to drop. `createTaskAddForm()` builds both add
fields so the sync guard cannot drift between them. **The chips fire on
`mousedown` with `preventDefault`, not `click`** — the field has to keep focus or
`isTaskTextEditing()` stops seeing an edit and the next poll re-renders the view
out from under a half-typed row.

`dueTime` had to be added to `normalizeTask()` in **both** `app.js` and
`server.cjs`, like `goalId` and `expiresOn`. It is advisory: it shows on the row
and in the placement bubble, but placement stays a click on the grid, because a
time typed into quick-add is an intention and auto-dropping the block would book
work that was never looked at on a day.

### Weekly digest

The `Week` output-panel tab. `weekDigest()` assembles the Monday–Sunday week
containing the selected date from records that already exist — calendar hours,
the goal log, rose/thorn answers, mistakes and their tags, finished albums,
survey averages — and `weekDigestText()` is what the Copy button emits. It lives

## Derived Logging (no user action)

Four things are recorded without anyone pressing anything. They exist because the
app was already producing this information and throwing it away.

- **Survey timing.** Surveys have no submit button, so `saveEntry` diffs the
  incoming `survey`/`checked` against the copy on disk and stamps
  `entry.<session>.surveyActivity` = `{ firstEditedAt, lastEditedAt, finishedAt,
  editCount }`. `finishedAt` only advances for saves landing inside the day's own
  window — midnight to 06:00 the next morning (`JOURNAL_DAY_END_HOUR`), because a
  Wednesday night survey is routinely filled in at 01:30 on Thursday. Editing an
  old entry moves `lastEditedAt` but not `finishedAt`. Prior values are read from
  the **disk** copy, never the incoming entry, so a stale browser tab that does
  not know the field cannot strip it.
- **Task reschedules.** The same diff compares open-section tasks by id and
  appends a `reschedule` row to `task-log.json` when a task's section or
  `dueDate` changes (`diffTaskSchedules`). Completed/discarded moves are endings,
  not reschedules, and are deliberately excluded. This is server-side precisely
  because the frontend would otherwise have to thread "why did this change"
  through every edit path.
- **Unanswered goals.** `finalizeUnansweredGoalDays()` runs at startup and
  hourly, and writes one `unanswered` goal event per materialised goal-day that
  is past the `backlogGraceDays` window and never got a response. `unanswered` is
  its own kind, not a `miss`: `checks / (checks + misses)` is adherence, and
  unanswered is coverage. Conflating them either invents failures or flatters the
  denominator. The sweep is idempotent — a day already carrying a response or an
  `unanswered` row is skipped.
- **App sessions.** See `app-log.json` above; `startAppSessionLog()` in `app.js`.
  The `end` row goes out through `navigator.sendBeacon` because the unload path
  cannot await a fetch, and `endAppSession()` guards against `pagehide` and
  `visibilitychange` both firing.

The Trends view surfaces the first three plus entry `_revision` — see below.

## Check how the text lands, not just the rule

A stylesheet edit that reads correctly is not a verified change. Before calling
any UI or copy work done, open the app in the preview browser, drive it into the
state you touched, and look at it. The recurring failure is not font size -- it
is text that no longer fits the box it was given and lands on top of something
else: a label running out over the field beside it, a button caption painted
past the edge of its panel, a caption clipped to "Deadl", two rows overlapping
because one of them grew a second line.

This is a blind spot, not bad luck. Reading CSS tells you what the rule says;
only the rendered page tells you what the human sees. The editor's kind row
("Plan / Actual / Deadline") sat in a 118px column for weeks, spilling its
buttons out over the panel, while every review of it was a review of the rule.

### The measurement

Overflow is measurable, so measure it rather than squinting. In the preview
browser, with the panel open:

```js
const b = document.querySelector('.calendar-editor-body');   // the container
const br = b.getBoundingClientRect();
const spill = [];
for (const el of b.querySelectorAll('*')) {
  const r = el.getBoundingClientRect();
  if (r.width && (r.right > br.right + 0.5 || r.left < br.left - 0.5)) spill.push(['box', el.className]);
  for (const n of el.childNodes) {                            // text nodes have no box, so range them
    if (n.nodeType !== 3 || !n.textContent.trim()) continue;
    const range = document.createRange();
    range.selectNodeContents(n);
    if (range.getBoundingClientRect().width > r.width + 0.5) spill.push(['text', n.textContent.trim(), el.className]);
  }
}
({ scrollW: b.scrollWidth, clientW: b.clientWidth, spill });
```

`scrollWidth > clientWidth` on a container means something inside it does not
fit. The text-node pass matters: a caption that overruns its label leaves no
element box outside the container, so an element-only check reports "clean"
while the screen shows the words crossing into the next column. Then still take
a screenshot -- overlap that stays inside the container measures as fine.

### Two mechanics behind almost all of it

- **Automatic minimum size.** A grid or flex item will not shrink below its
  min-content width unless it is given `min-width: 0`. A date or number input's
  min-content is the browser's own default box, so the input silently widens the
  track it lives in past the column, which stops the caption above it from
  wrapping and pushes both out sideways. A `<fieldset>` is worse: its default
  `min-inline-size` is `min-content`, so it refuses to shrink into its track at
  all and simply paints outside it.
- **A single word cannot wrap.** "Deadline" in a 39px track does not break, it
  overflows. Any label that must survive a narrow column needs either a column
  wide enough for the longest word or `overflow: hidden` so the failure is a
  clip inside its own box rather than a smear across its neighbour.

### The states worth putting on screen

One screenshot of the happy path is not coverage. For the calendar editor that
means: each kind (plan / actual / deadline, since each shows and hides different
fields), a saved event as well as a new one (a saved deadline adds the work-plan
status row), an event that spans days (a second date field appears), a synced
event (read-only fields), the time-zone and transit panels open, and the phone
width -- the editor's body is a fixed three-column grid on the desktop and used
to scroll sideways on a 375px screen. Elsewhere the same rule applies to the
longest real string, not a short placeholder: the longest task title, a person's
full name, a category with every letter chip filled.

## Editing Conventions

- Prefer existing patterns in `app.js`; it is a single-file frontend app.
- Never call a UI or copy change done from the diff alone. Render it and look at
  the text, in every state it has -- see "Check how the text lands, not just the
  rule" above.
- Keep edits narrow. This app contains live personal data and UX experiments.
- Use `apply_patch` for code edits.
- Avoid touching generated/user data unless required.
- Do not revert unrelated user changes.
- After changing launchers or HUD behavior, the user must close/reopen the HUD or app window to see native-window changes.
